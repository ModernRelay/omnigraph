- **CLI exits follow the disposition.** For the data commands the CLI classifies (reads, data writes, aliases and target commands), a failure whose effects are unknown, or partial because an earlier step published, exits 2 instead of 1; one with no effects still exits 1, a busy refusal 75 and a failed condition 4, and a server refusal stating `effects: none` with `retry` now also exits 75. An embedded write's own refusal now carries the engine's disposition, as a server's does, so embedded load conflicts and failed conditions exit as served ones (1 and 4) instead of claiming unknown effects. A command line the argument parser refuses exits 64 instead of 2 (an addressing refusal inside a command still exits 1), and a failure whose diagnostic cannot be delivered keeps its exit. Maintenance commands, `cluster`, `policy` and managed commands keep their own exits for now. Read commands, `alias` included, report the same failure envelope as data writes, with `disposition` (always `effects: none`) on stdout in JSON mode and on stderr in human mode. Managed commands keep their own exits for now. Update scripts that read exit 2 as a usage error or exit 1 as every failure. See [failed commands][cli-exit-outcomes].
