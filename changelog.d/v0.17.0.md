Omnigraph 0.17 tells every credential which graphs it can use. A graph that
gives the caller no permission answers "graph not found". MCP refuses a read
that is too large for an agent to take in. New graphs use storage format 18,
which records each branch in the catalog of `main`. Cleanup sends fewer
storage requests, and concurrent traversals use less memory. Existing
format-17 graphs need no rebuild. Upgrade every reader and writer before you
create a format-18 graph. Upgrade the CLI and the server together. Rust hosts
of `omnigraph-mcp` must change some calls.

## Why these changes

The old graph listing did not use the rules that control access to a graph.
Some callers saw graphs that they cannot use. Other callers saw no graphs.
Agents lost MCP results that were larger than the client accepts. A branch
was a set of files with its own recovery rules. Now one catalog commit
records it.

## Highlights

### Every credential can ask which graphs it can use

`graphs list` needed the server's `graph_list` permit, which a cluster with
no policy grants to nobody, so a static token or an OAuth client got 403. The
discovery route listed every graph to an identity, including graphs it could
not open. Now listing and routing use one rule: a caller sees a graph when it
holds any permission on it, and every other graph answers `graph not found`,
exactly as an absent one does. The listing states its rule
(`visibility: granted`) and names the caller's actor. An MCP client gets a
`setup` link when the list is empty, and a read over 96 KiB is refused with
`result_too_large` instead of being cut off by the client: Claude Code moves
a result over 50,000 characters to a file. #1544, #1526

### Branches are entries of the catalog: format 18

A branch existed as Lance ref files, and deleting one took three writes with
three recovery rules, ordered only by a lock inside one process. On a
format-18 graph a branch is one entry of `main`'s catalog, published by
compare-and-swap with the rest of the graph. A crash between steps leaves a
branch that refuses as `branch_not_ready` or `branch_deleted` until the next
`branch delete` ends it. In the seeded storage-cost run (simulated store), a
branch delete sends 17 storage requests instead of 25, and a write on a
branch 17 instead of 22. This is the first step toward branch create and
delete from several writer processes; one writer process per graph is still
the supported setup. #1504, #1542

### Cleanup: 20 delete requests instead of 36

`cleanup` sent one request per freed file and opened each removed version
twice. It now sends a table's freed files as one bulk delete (S3
`DeleteObjects`, up to 1,000 keys) and opens each version once. After 16
one-row inserts, `cleanup --keep 1` on RustFS sent 20 delete requests instead
of 36, 38 HEADs instead of 60 and 35 GETs instead of 57. Through a proxy that
adds 20 ms per request it took 3.8 s instead of 5.1 s (a 2-core VM, not a
cloud store). #1502

### Eight concurrent traversals: 886 MiB instead of 3,550 MiB

After an edge write, every traversal that missed the cache built its own
in-memory adjacency, outside the query memory budget, so a burst of
traversals multiplied memory. Now traversals that miss together build it
once and share it, and a read at a past commit uses the same cache. On a
local graph of 2 million nodes and 3.5 million edges, eight cold one-hop
queries peaked at 886 MiB instead of 3,550 MiB in the same time (dev build,
one run). #1540

### Google Cloud Storage roots, in preview

A graph could reach Google Cloud Storage only through its S3 interoperability
endpoint, with long-lived keys and no documented support for conditional
writes. The embedded Rust API now opens `gs://bucket/prefix` roots with the
workload's own credentials, and every commit is conditioned on the object
generation, so exactly one writer wins each version. The CLI, the server and
cluster roots refuse `gs://` for now. CI tests `gs://` graphs against a
simulated bucket, not Google's service. #1462
