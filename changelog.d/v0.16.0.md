Omnigraph 0.16 checks access on direct cluster writes.
A graph without a policy denies reads by default. A request cannot raise
its budget above the server's limit. A cluster server can compact datasets
while it serves. Completed compaction survives a later index failure.
Small keyed writes and repeat reads send fewer storage requests.
Existing format-16 graphs need no rebuild. Upgrade every reader and writer
before creating a format-17 graph. See the upgrade actions for changes to
login, token files, maintenance APIs and `repair`.

## Why these changes

A static token could read graphs without a policy. Direct cluster writes
and embedded maintenance skipped policy checks. Login could silently select
an organization. Callers could raise their own budgets. Another local
account could add tokens through a writable token file. `repair` held write
locks to list unused commits. Format 17 lets a branch reject a writer
after its replacement claims ownership.

## Highlights

### Servers refuse what the operator did not grant

Any static bearer token could read every graph that had no applied policy, and
any request could raise its own memory and work budgets without limit. Any
credential could also crash the server, and every graph with it, with one MCP
tool call or a deeply nested query. Now a graph with no policy refuses every
action (default deny), a budget above the server's default gets a 400, each MCP
tool call runs in its own heap allocation, and query nesting is bounded before
parsing. The server also refuses a token file that other accounts can write,
and a static actor named like a signed identity. #1323, #1324, #1327

### Compaction keeps completed work when an index fails

On a 657-table production graph, an optimize run that changed nothing held
up writes for 577 seconds, measured from outside the server's region.
With `--max-gate-hold`, the first dataset runs and the deadline stops further
datasets from starting. Writers still wait for work already started, publication
and configuration cleanup. Use `--datasets` to select datasets. If an index
step or its final coverage check fails after compaction, the completed work
publishes once. The report marks the dataset `optimized` with reason
`index_failed` and includes the error. On a server, submitting the same
request with its retained operation ID returns the existing record. A new
operation rechecks coverage and retries any remaining index work. Operators
upgrading from an early edge build can find the operation-record recovery
procedure in the upgrade actions. #1275, #1282, #1415, #1418, #1478, #1479

### Direct optimize runs up to eight compaction tasks at once

At the default concurrency of eight, direct `optimize` can run eight
compaction tasks or build up to four independent B-tree indexes at once.
Each Blob table still runs one compaction task at a time. A full-text or
vector build uses all available slots. Served `optimize` runs one task at
a time. If a dataset exceeds a server limit, another run defers it again.
Raise the limit or optimize it directly. #1396, #1395, #1441

### Keyed writes: 34 storage requests instead of 212

A one-row keyed write scanned the key column of every fragment, so its cost
grew with the table. It now probes the identity index while the unindexed tail
is small: at 262,144 rows in 64 fragments, an update sends 34 requests instead
of 212 and an insert 18 instead of 83 (simulated store, not S3). A traversal
after a write or branch change rebuilds topology only for the edge tables that
changed: 26 requests instead of 59 at 131,072 edges. A `limit` with no filter
reaches the Lance scanner and reads 1 of 25 data files instead of 16 on local
disk. On a server, repeat commit lookups open only the branch that holds them;
a hosted graph with nine branches took 13 s per lookup before, and the hosted
gain is not yet measured. #1318, #1363, #1342, #1184

### Spilling queries finish within their memory budget

A correlated block that reads the outer row, such as `max($b.x) { … } > 0`,
collected every inner match before folding them, so a large fan-out ran out of
`query_memory_bytes`: 16,384 one-KiB inner rows were refused at 12 MiB, and now
complete there (local disk). A query whose sort spilled could fail at one
budget yet pass at smaller and larger ones; its merge now reserves 9.4 MiB
instead of 40 at the default 150 MiB and stays within half the budget. Spill
files are zstd-compressed: the whole-query spill test wrote 5.9 MB instead of
52.6 MB. #1341, #1362, #1389, #1348
