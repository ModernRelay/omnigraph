Omnigraph 0.16 makes a server refuse what its operator did not grant. A graph
with no policy refuses reads. A request cannot raise its budgets above the
server's. Two requests that crashed the server are fixed. `optimize` can limit
how long writes wait, and a cluster server can run it while it serves. Small
keyed writes and repeat reads send fewer storage requests. The upgrade actions
change server access, token files, maintenance APIs and `repair`. New graphs
use storage format 17, which 0.15 cannot open. Read the upgrade actions before
you upgrade.

## Why these changes

Each change closes a gap between what an operator configured and what the
server allowed. A static token could read every graph that had no policy. A
caller could raise its own memory and work budgets. Another local account could
add a token through a writable token file. Embedded maintenance ran without a
policy check. `repair` held every write lock to list commits that nothing
reads. Format 17 records a branch's writer epoch, which older binaries cannot
read.

## Highlights

### Servers refuse what the operator did not grant

Any static bearer token could read every graph that had no applied policy, and
any request could raise its own memory and work budgets without limit. Any
credential could also crash the server, and every graph with it, with one MCP
tool call or a deeply nested query. Now a graph with no policy refuses every
action (default deny), a budget above the server's default gets a 400, each MCP
tool call runs in its own heap allocation, and query nesting is bounded before
parsing. The server also refuses a token file that other accounts can write,
and a static actor named like a signed identity. #1323, #1324, #1327

### `optimize` no longer holds writes for the whole run

Optimize held main's writer gates from start to finish: on a 657-table
production graph, a pass that changed nothing held them for 577 s (measured
from outside the server's region). A cluster graph could be optimized only with
its server stopped. A writer during optimize prepared nearly every write twice
and finished 85 writes in 90 s instead of 535. Now `--max-gate-hold` starts no
table after its bound, so a write waits about the bound plus one table, and
each table reports its own outcome. A cluster server runs optimize as a
recorded operation, off by default. A write that meets an optimize commit is
carried over it: in a rerun on RustFS with debug builds, every write succeeded
without a 409. #1275, #1282, #1349

### Keyed writes: 34 storage requests instead of 212

A one-row keyed write scanned the key column of every fragment, so its cost
grew with the table. It now probes the identity index while the unindexed tail
is small: at 262,144 rows in 64 fragments, an update sends 34 requests instead
of 212 and an insert 18 instead of 83 (simulated store, not S3). A traversal
after a write or branch change rebuilds topology only for the edge tables that
changed: 26 requests instead of 59 at 131,072 edges. A `limit` with no filter
reaches the Lance scanner and reads 1 of 25 data files instead of 16 on local
disk. On a server, repeat commit lookups open only the branch that holds them;
a hosted graph with nine branches took 13 s per lookup before, and the hosted
gain is not yet measured. #1318, #1363, #1342, #1184

### Spilling queries finish within their memory budget

A correlated block that reads the outer row, such as `max($b.x) { … } > 0`,
collected every inner match before folding them, so a large fan-out ran out of
`query_memory_bytes`: 16,384 one-KiB inner rows were refused at 12 MiB, and now
complete there (local disk). A query whose sort spilled could fail at one
budget yet pass at smaller and larger ones; its merge now reserves 9.4 MiB
instead of 40 at the default 150 MiB and stays within half the budget. Spill
files are zstd-compressed: the whole-query spill test wrote 5.9 MB instead of
52.6 MB. #1341, #1362, #1389, #1348
