## Upgrade actions

- Branch names are used exactly as written. A name with leading or trailing
  whitespace or a control character is now refused as a bad request wherever
  a branch is named (HTTP routes, CLI commands and embedded engine calls), as
  branch statements already refused it; such a name used to be trimmed, so
  `main ` named `main`. Clients that send padded names must send the exact
  name. A policy whose `protected_branches` lists such a name now fails
  validation. See [branch names][branch-names-as-written].

[branch-names-as-written]: ../user/branching/index.md#branch-names

- `omnigraph version --json` now reports target and credential protocol 2 for the current operator configuration and credential commands. Clients selecting a CLI must require these exact versions: protocol 1 appeared in multiple incompatible edge builds and cannot identify one format. The YAML document remains `version: 1`; see [compatibility discovery][cli-protocol-discovery] and the [configuration upgrade guide][cli-protocol-upgrade].

[cli-protocol-discovery]: ../user/install.md#verify
[cli-protocol-upgrade]: ../user/cli/targets.md#upgrade-from-the-old-format

- **CLI exits follow the disposition.** For the data commands the CLI classifies (reads, data writes and aliases), a failure whose effects are unknown, or partial because an earlier step published, exits 2 instead of 1; one with no effects still exits 1, a busy refusal 75 and a failed condition 4, and a server refusal stating `effects: none` with `retry` now also exits 75. An embedded write's own refusal now carries the engine's disposition, as a server's does, so embedded load conflicts and failed conditions exit as served ones (1 and 4) instead of claiming unknown effects. A command line the argument parser refuses exits 64 instead of 2 (an addressing refusal inside a command still exits 1), and a failure whose diagnostic cannot be delivered keeps its exit. Maintenance commands, `cluster`, `policy`, `target`, `credential` and managed commands keep their own exits for now. Read commands, `alias` included, report the same failure envelope as data writes, with `disposition` (always `effects: none`) on stdout in JSON mode and on stderr in human mode. Managed commands keep their own exits for now. Update scripts that read exit 2 as a usage error or exit 1 as every failure. See [failed commands][cli-exit-outcomes].

[cli-exit-outcomes]: ../user/operations/troubleshooting.md#failed-data-write-commands

- Create profiles explicitly with `login --create-profile NAME`; ordinary login and managed target discovery honor `defaults.profile`. Standalone targets now use one flat `auth` provider: remove named auth maps and `default_auth`, use separate targets for different identities, and reinstall their stored tokens with `credentials set --target NAME --stdin`. The old `--register`, `--auth`, `target register`, and `config rename-auth` spellings are removed. Target listing now shows destinations, managed profiles, and the default marker. See [operator configuration][cli-profile-consistency].

[cli-profile-consistency]: ../user/cli/targets.md

- The CLI now selects one complete backend with `--target NAME|ADDRESS` or `defaults.target`. Legacy routing flags, profiles, folder selection and `use` are removed; `--config` supplies source files only, and resolved targets and known write scopes are always printed to stderr. Cloud bindings preserve native authentication while pinning destination, signing and conditional-write settings; unsupported ambient transport overrides refuse. Run `omnigraph target import` for legacy operator configuration and lifecycle custody, then review the complete target and endpoint-bound credentials before use. See the [CLI reference][target-cli].

[target-cli]: ../user/cli/reference.md

- The CLI no longer reads `OMNIGRAPH_BEARER_TOKEN`. It used to send that
  token to any remote server a command addressed, including a literal
  `--server https://…` URL the operator does not control. A token now reaches
  only the server it is keyed to: a request to a URL under a server declared
  in `~/.omnigraph/config.yaml` carries that server's token, and any other
  request carries none. When such a request gets HTTP 401, the CLI names the
  server to declare or the `omnigraph login` command to run; `--json` output
  carries this as `missing_credential` beside the server's unchanged error.
  The server's own `OMNIGRAPH_SERVER_BEARER_TOKEN*` settings are unchanged.

  If you export `OMNIGRAPH_BEARER_TOKEN` for the CLI, declare the server under
  `servers:` and bind its token with `omnigraph login <name>`, or set
  `OMNIGRAPH_TOKEN_<NAME>` (the name uppercased, `-` written as `_`). In CI,
  write a `config.yaml` with the server's `url` into `$OMNIGRAPH_HOME` and
  pass the secret as `OMNIGRAPH_TOKEN_<NAME>`. Address the server by name
  (`--server <name>`) or by a URL under its `url`. Managed credentials
  (`omnigraph login --api`, `OMNIGRAPH_CONTROL_TOKEN`) are unchanged. See
  [server credentials][cli-unkeyed-bearer-token-removed].

[cli-unkeyed-bearer-token-removed]: ../user/cli/index.md#use-a-server

- Saved query plans now use envelope version 9, which records each correlated block's strategy. Regenerate plans saved with earlier binaries; older binaries reject version 9 plans.

- Saved query plans now use envelope version 7 to preserve distinct-count semantics. Regenerate plans saved with earlier binaries; older binaries reject version 7 plans.

- Vectors written by an earlier `omnigraph embed` embed the templated text
  rather than the source value and match text queries poorly. Regenerate them
  with `omnigraph embed --reembed-all` and load the result again. An embedding
  spec, including a seed manifest's `embeddings` entry, must now list exactly
  one property in `fields`, the source its `@embed` declares; a spec that
  lists several is refused, and so is a source value that is not a string.
  See [the offline file pipeline][embed-exact-source-text-pipeline].

[embed-exact-source-text-pipeline]: ../user/search/embeddings.md#offline-file-pipeline

- **Every error code names the statuses it is sent under.** A Blob `If-Match` that fails
  answers `412` `precondition_failed` instead of `conflict`, and `408`, `413`,
  `415` and `416` answer `request_timeout`, `payload_too_large`,
  `unsupported_media_type` and `range_not_satisfiable` instead of
  `bad_request`, a resource limit's `413` included. A write the server could
  not settle answers `500` `outcome_unknown` whatever failed underneath, and
  every `503` that asks for a retry, a graph that is not served or closed
  admission, carries `Retry-After` as a `429` does. `ErrorCode` in
  `openapi.json` names each code's statuses and meaning, two for
  `branch_start_refusal` (`409`, and `410` for a commit that is no longer
  retained), every protected operation documents the `404` and `405` its
  router answers, and header
  parameters are published as `Omnigraph-Http-Api` and
  `Omnigraph-If-Actor`. Update clients that matched those refusals by
  `conflict` or `bad_request`, and regenerate clients that key on header
  parameter names. See [HTTP errors][error-code-statuses-guide].

[error-code-statuses-guide]: ../user/operations/troubleshooting.md#http-errors

- **Every error says what it did and what to do next.** Server error bodies
  carry a `disposition` object computed by the server for the request it
  answered. `effects` is `none`, `partial` when an earlier step of the same
  operation published and the failing step was refused before it wrote
  anything (a load that forked its missing branch), or `unknown`. `action` is
  `fix` for a request the caller must correct (its credential, input, path or
  client), `refresh` for a refusal by the state it met, `retry`, `recover` or
  `reconcile`. A write whose completion the server could not settle answers
  `code: outcome_unknown` instead of `internal`; a failure the engine proved
  published nothing keeps its code, with `effects: none`, or `partial` after an
  earlier step published. Errors that had no `code` now
  have one: `precondition_failed`, `recovery_required`, `external_blob_source`
  and `change_feed_gap`, beside their details, and a deployment status read
  that raced an owner change answers `service_unavailable`. Refusals that
  answered in plain text now answer the same body: an unknown route (`404`), a
  method the route does not serve (`405`), and a malformed body, query string
  or path parameter, where a JSON body that failed to deserialize answered
  `422` and now answers `400`. CLI data-write failures print the same
  `disposition` field in place of `command_outcome`, whose `execution` is gone
  (`not_started` is `effects: none`), taking the server's when its request was
  the command's only effectful one. Update clients that read `command_outcome`,
  or that told those errors apart by a missing `code` or a `422`. In
  `openapi.json`, `error`, `code` and `disposition` are required on every error
  body, and the optional query parameters of `GET /snapshot`, `GET /commits`
  and `POST /load/ndjson` are declared as their plain type (`string`, `integer`
  or `LoadMode`) instead of a union with `null`; they stay optional, so
  regenerate clients built from the earlier description. See
  [failed data-write commands][error-outcome-guide].

[error-outcome-guide]: ../user/operations/troubleshooting.md#failed-data-write-commands

- Consumers of saved explain documents must accept `explain_version` 5 and its new pipeline shape: `pipelines` entries now carry identity, a pipeline `id` and `depends_on` naming the build pipelines drained before it starts, with `source`, `operators` and `sink` as objects whose `id` joins the `physical_plan` node ids. The push executor builds from the same decomposition the document serializes, so the printed pipelines are the executed ones. The additive `logical_plan_initial` field holds the logical plan as resolved, before rewrite passes ran, and `explain` output prints it as the `logical_initial` tree.

- A full-text call (`search`, `fuzzy`, `match_text`, `bm25`) on a String
  property the schema does not index is refused at type checking (`T27`).
  Such a call used to scan with a bare, case-sensitive tokenizer, so
  `search($d.notes, "deep")` missed `"Deep Learning"` while the same call on
  an `@index` property matched both spellings. Declare `@index` on the
  property; every write then records the index's analyzer. An enum takes no
  full-text index: compare its values with `=`.

  Stored queries are recompiled when a server starts, and a refused one
  quarantines its graph. Run `omnigraph queries validate` and
  `omnigraph cluster plan` before upgrading, and treat a `T27` finding as a
  pre-upgrade fix. See the [search guide][full-text-index-search].

- A branch's `__manifest` now keeps a block registry of its released history:
  one `history_block` row per released run of a `__history` block and one

  crosses released history without reading its blocks and reads `__history`

  and generation.

- An embedded `Session` can replace or clear one Blob value of an existing
  node or edge by exact id with `put_blob_at_as` and `clear_blob_at_as`. Each
  write is one graph commit under the `change` action, never reads the old
  value, and carries the row's other cells as an `update` does. An optional
  precondition, `BlobPrecondition::Tags` (the current ETag is one of the given
  tags) or `BlobPrecondition::AnyExisting` (the cell is not null), fails with
  `BlobWritePreconditionFailed`, which names the current ETag, and changes
  nothing. A put returns the value's length, its ETag and the commit; the ETag
  is the one a read at that commit reports. One put holds at most the
  session's `write_max_bytes` (32 MiB by default), inclusive; a larger one
  fails before any table is opened with resource `Blob write payload bytes`.
  The HTTP server exposes them as `PUT` and `DELETE /blob`, and the CLI as
  `blob put` and `blob clear`.

- `omnigraph blob put ENTITY TYPE ID PROPERTY` stores the raw bytes of
  `--file PATH` or stdin in one Blob cell, and `omnigraph blob clear` sets a
  nullable cell to null, on a `--store` graph or a served one. Both take
  `--branch`, `--if-match TAG` (`*` or entity tags) and `--json`, and print the
  receipt the server returns: the selector, branch, state, size and ETag of a
  managed value, the actor and the exact commit, which is `null` for a clear of
  a cell that was already null. Input over 32 MiB and a malformed `--if-match`
  are refused before the graph is addressed, and an interactive stdin is
  refused rather than waited on. `--as` names the actor of a `--store` write.
  A served Blob precondition failure exits 4, as a graph-commit one does; an
  embedded one exits 1. A write is sent once and never retried.

- `PUT` and `DELETE /graphs/{graph_id}/blob` replace or clear one Blob value
  of an existing node or edge, each as one graph commit under the `change`
  action. `PUT` takes a raw `application/octet-stream` body of at most 32 MiB,
  inclusive (`415` for another media type, `413` over the limit, refused
  before reading when `Content-Length` declares it, `408` past the body
  deadline). Both take `branch`, default `main`, refuse `snapshot`, and accept
  `If-Match`: `*` or a list of entity tags. A failed `If-Match` is a `412`
  with the new `blob_precondition_failure.current_etag` detail and an `ETag`
  header naming the cell's current value. Success returns a receipt with the
  selector, branch, `kind` (`managed` or `null`), `size` and `etag`, the actor
  and the exact `commit`, which is `null` only when clearing a cell that was
  already null. A `PUT` also returns the `ETag` header.

- Unattached graph branches (RFC "Unattached graph branches"): a mutation
  declaration may end in `as unattached branch`, optionally `on "<id>"` or
  `on $base`, which writes the complete result as an unattached snapshot,
  readable by its graph commit id (`kind: "unattached"`, `published: false`
  and `root_commit_id` on the receipt's `commit`), invisible to every branch
  read, and extendable by a further write `on` it; the caller holds the
  latest id as its tip, and two writes on one base each get their own
  snapshot. A snapshot never publishes: `commit publish "<id>"` and
  `POST /commits/{commit_id}/publish` answer 409 with the error code
  `unattached_cannot_publish`. `commit drop "<id>"` and
  `DELETE /commits/{commit_id}` drop the snapshot and every snapshot built
  on it; `GET /commits?unattached=true&branch=<name>` and the CLI's
  `commit list --unattached` list a branch's live snapshots, newest first.
  Every snapshot of a chain expires when its branch head moves past the head
  the first write captured or the branch is deleted. Writing is a `change` on
  the recorded branch; a child accepts an omitted branch and refuses an
  explicit branch that differs from its base's target, including `main`.
  Listing and snapshot reads need `read` on that target. Missing ancestry
  prevents reads, extension and drop and retains the snapshot during cleanup.
  `CommitOutput` gains `kind` and `root_commit_id`; clients infer legacy
  receipts' kind from `published` when the kind field is absent. A graph born by this release is stamped
  internal schema v16; v14 and v15 graphs stay served and refuse
  `as unattached branch` until `omnigraph upgrade` stamps their live branches.
  GQT cases name a bound snapshot in `as unattached branch on "${name}"`.

- Unpublished graph commits (RFC "Unpublished graph commits"): a mutation
  declaration or a `branch merge` statement may end in `as commit`, which
  writes the complete result as an unpublished commit, readable by its graph
  commit id (`published: false` on the receipt's `commit`) and invisible to
  every branch read, until `commit publish "<id>"` installs that exact result
  on its recorded target branch or `commit drop "<id>"` removes it. Both are
  control writes through `POST /mutate` and have routes of their own,
  `POST /commits/{commit_id}/publish` (the published commit) and
  `DELETE /commits/{commit_id}` (204); `GET /commits?unpublished=true` lists
  a branch's unpublished commits, `POST /branches/merge` takes `as_commit`
  (exclusive with `delete_branch`), and the CLI gains `commit publish <id>`,
  `commit drop <id>`, `commit list --unpublished` and `branch merge
  --as-commit`. `CommitOutput` gains `published`.
  Two Cedar actions, `commit_publish` and `commit_drop`, gate the control
  writes by the recorded target (`target_branch_scope`). A graph born by this
  release is stamped internal schema v15; v14 graphs stay served and refuse
  `as commit` until `omnigraph upgrade` stamps their live branches. GQT cases
  bind a write's commit id with `--- bind commit $name`, read it with
  `--- query snapshot: $name`, and name it in `commit publish "${name}"` /
  `commit drop "${name}"`.

- Bounded writes now accept the [`write_max_bytes` session setting][write-max-bytes],
  from `1` through `33554432` bytes (the unchanged 32 MiB default), with
  `OMNIGRAPH_WRITE_MAX_BYTES` supplying the process default.
  Row data and logical Blob payloads have independent allowances, so a Blob exactly
  at the limit can accompany scalar metadata that fits its own allowance.
  The default now admits up to 32 MiB of row data plus 32 MiB of Blob payload
  per operation, where the previous single 32 MiB allowance covered both.
  HTTP body, Blob read, compaction and URI metadata limits remain independent.

## Behavior changes

- Correlated block aggregates now use the same result types as return
  aggregates: integer `sum` accumulates exactly in 128 bits and rounds once
  to `F64` before comparison, `avg` converts each input to `F64` before
  accumulation, `min` and `max` retain the column's type and full `U64` range,
  and counts refuse values beyond `I64`.
  A single integer sum of `9007199254740993` therefore no longer satisfies
  `> 9007199254740992` after rounding.
  Regenerate saved bound plans; see the [query guide][block-aggregate-guide].

[block-aggregate-guide]: ../user/queries/index.md#correlated-blocks

- On S3 cluster roots, a server's cluster lock now carries a lease renewed by
  heartbeat objects under `__cluster/lease/`. A server restarted after a crash
  takes over its predecessor's lock once the heartbeats have been silent for a
  lease and a half (45 seconds by default, `OMNIGRAPH_CLUSTER_LEASE_SECONDS`),
  so an orchestrator's restart-on-failure policy recovers without
  `cluster force-unlock`. An owner none of whose heartbeats is answered for two
  thirds of a lease stops every storage write and exits 2. Local and Azure
  roots, and CLI writers, keep the exact-ID unlock. Older binaries refuse the new version-3 lock record. See
  [restart after a failure][cluster-lock-lease].

[cluster-lock-lease]: ../user/operations/storage-failures.md#restart-after-a-failure

- A named traversal whose hop bound allows more than one hop is refused with
  `T5` when its edge connects two different node types, as in
  `$p worksAt{1,2} $c` for `WorksAt: Person -> Company`. No path over such an
  edge continues past its first hop. Before, such a range was capped at one
  hop without a word: `{1,n}` returned the one-hop rows, and a range starting
  above one, such as `{2,2}`, returned none. For `{1,n}`, omit the bound or
  write `{1,1}` to keep the same rows. A range starting above one never
  matched anything, and dropping its bound would return the one-hop rows
  instead, so check which path the query meant. A stored query with such a
  bound now fails type checking, which `omnigraph queries validate` reports.
  See [traversal and match patterns][cross-type-hop-bound-refused-traversal].

[cross-type-hop-bound-refused-traversal]: ../user/queries/traversal.md

- Dropping a property no longer rewrites its table. Through v0.13.0 schema
  apply rewrote the table without the dropped values, so `omnigraph cleanup` alone
  erased them; now they stay in the table's data files until
  `omnigraph optimize` rewrites every fragment that holds them, whatever its
  size. To erase them, run optimize, delete every branch created from a commit
  before it and every tag naming such a commit (merging a branch does not
  release its files), then run `cleanup` with a retention that excludes the
  commits before the optimize, for example `--keep 1`. Dropped types are still
  reclaimed by `cleanup` alone. See
  [dropping declarations][dropped-property-storage-drops].

- `branch merge` now selects its base as the newest commit both branches descend from. ## Performance

- A read on a warm graph handle checks for new commits by asking for its
  `__manifest` version and the next one by name instead of listing the version
  directory. On S3-compatible storage that listing returned up to 1,000 keys
  on every read once a branch passed 1,000 commits; the check is now two small
  HEAD requests sent together while nothing changed. See the
  [catalog freshness probe][freshness-probe].

[freshness-probe]: ../dev/lance.md#current-compatibility-fences

- **Fewer, larger change pages from the CLI.** When `commit changes`,
  `changes poll`, `diff` or `branch diff` follows every page itself, it now
  asks for 8,192 changes per page instead of the 1,000 the HTTP routes
  default to. Every page restarts its comparison after the last change the
  previous page returned, so fewer, larger pages cost fewer requests and
  less time; the output is unchanged. `--limit` still sets the size, and a
  single `--page-token` fetch still defaults to 1,000. See
  [changes and change feeds][cli-change-pages].

[cli-change-pages]: ../user/branching/changes.md#inspect-one-commit

- A correlated block (`not { ... }`, `count { ... }`, and the block aggregates)
  that reaches the outer row only through one binding's identity and binds one
  of its own nodes by a key or unique equality now runs once from that node,
  when its row estimate is lower, instead of expanding every outer row's
  binding. Explain reports the choice as the `AntiJoin` row's `strategy`. See
  the [query guide][key-set-blocks].

[key-set-blocks]: ../user/queries/index.md#correlated-blocks

- Export and the change-feed baseline read the managed Blob values of each
  batch of rows with one planned read per Blob column instead of one read per
  row, and change-feed images and entity reads use the same reader for their
  row. Memory stays bounded by one row's values plus, per Blob column, an
  8 MiB read buffer or one larger value. See
  [Blob maintenance and export][export-batched-blob-reads].

[export-batched-blob-reads]: ../dev/blob.md#maintenance-and-export

- A `load csv` overwrite now writes its Lance files through up to
  `stage_write_concurrency` writers at once (default 8) instead of one after
  another: the validated batches are cut into contiguous runs of at most one
  Lance file (1 M rows), each run is one writer, and the files are published in
  input order, so a table's files are the ones a single writer would have
  produced. The setting's description names this second use beside the
  cross-table width it already controlled.

- A `load csv` overwrite now parses its source in up to
  `stage_write_concurrency` streams at once (default 8) instead of one: the
  source is cut on record ends into 8 MiB slices, each stream claims the next
  slice as it finishes one, and the validation puts the slices back in source
  order before judging them, so the rows, their order and a refusal's record
  are those of a single parser. A source under 8 MiB still parses in one
  stream. The explain's `pipelines` entries carry `partitions`, the receipt's
  `executed.operators` carry `partitions` and, on the source, one `slices`
  entry per slice (its rows, the stream that claimed it and its timings), and
  a GQT `load pipeline` line may claim `partitions <n>`.

- A `load csv` overwrite into an edge type whose endpoint node types carry a
  single integer `@key` (`I32`, `I64` or `U32`) now checks every edge's `__src`
  and `__dst` against an integer key set built once per endpoint table, read
  straight from the held batches, instead of copying each edge's id and
  endpoints into strings and probing string sets row by row. Which edge is
  refused, and with which message, is unchanged; endpoint types keyed by text
  or `U64` keep the previous check. The planner now counts the key list a
  probe builds, one entry per input row, so an endpoint check whose node
  table has no usable `__id` index plans `scan` (one read of the id column)
  instead of a probe with one literal per edge endpoint; `explain` shows the
  access and both costs. A usable index with partial or unknown coverage is
  costed as a full one, so a small key list keeps its filtered probe and a
  large one scans. Integer sets, their build buffers and a probe's key list
  are admitted against `query_memory_bytes`; oversized hash buckets use
  bounded binary searches.

- A load statement now shares its committed-state reads: validation opens one
  statement-scoped Lance session with held table handles and a byte-range memo,
  so identical metadata, index and data reads are fetched once per statement
  instead of once per check. The reuse buffers are admitted against
  `query_memory_bytes`, which now also bounds this load-statement state; an
  allowance that cannot admit them keeps the previous uncached reads. See the
  [settings guide][load-reuse-settings].

[load-reuse-settings]: ../user/queries/settings.md

- Merges into independent target branches on one handle no longer queue
  behind each other. A merge that misses the handle's single-entry authority
  cache now reopens that branch's coordinator without holding the cache's
  lock, so concurrent merges into different targets overlap; merges into the
  same target still serialize.

- Automatic traversals price missing or incomplete edge indexes during planning. Explain reports index facts at the pinned dataset version; older saved plans retain their coverage checks. See the [explain guide][planner-index-facts-explain].

[planner-index-facts-explain]: ../user/queries/explain.md

Root scans now record and execute their planned scalar-index access. Explain and GQT expose probes and residuals. Single String key equality can use the identity BTREE while retaining its original predicate; older saved plans retain their index defaults.

- Adding a nullable property, renaming a property and dropping a property no
  longer rewrite the table. Schema apply changes only the table's metadata, so
  its memory and I/O no longer grow with the rows and Blob values the table
  stores, only with its metadata (fragments, columns and indexes): a schema
  change on a large Blob table, which previously held every managed Blob value
  of the table in memory and could exhaust a server running the deployment,
  now reads no row and no Blob value. Existing indexes keep covering their rows
  instead of waiting for the next `optimize`, and a stored external Blob
  reference to a byte range, which schema apply previously refused, is kept as
  stored. See [schema changes][schema-apply-metadata-only-changes].

[schema-apply-metadata-only-changes]: ../user/schema/index.md#schema-changes
