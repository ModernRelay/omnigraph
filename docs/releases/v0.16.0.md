Omnigraph 0.16 makes a server refuse what its operator did not grant. A graph with no policy refuses reads. A request cannot raise its budgets above the server's. Two requests that crashed the server are fixed. `optimize` can limit how long writes wait, and a cluster server can run it while it serves. Small keyed writes and repeat reads send fewer storage requests. The upgrade actions change server access, token files, maintenance APIs and `repair`. New graphs use storage format 17, which 0.15 cannot open. Read the upgrade actions before you upgrade.

## Highlights

### Servers refuse what the operator did not grant

Any static bearer token could read every graph that had no applied policy, and any request could raise its own memory and work budgets without limit. Any credential could also crash the server, and every graph with it, with one MCP tool call or a deeply nested query. Now a graph with no policy refuses every action (default deny), a budget above the server's default gets a 400, each MCP tool call runs in its own heap allocation, and query nesting is bounded before parsing. The server also refuses a token file that other accounts can write, and a static actor named like a signed identity. #1323, #1324, #1327

### `optimize` no longer holds writes for the whole run

Optimize held main's writer gates from start to finish: on a 657-table production graph, a pass that changed nothing held them for 577 s (measured from outside the server's region). A cluster graph could be optimized only with its server stopped. A writer during optimize prepared nearly every write twice and finished 85 writes in 90 s instead of 535. Now `--max-gate-hold` starts no table after its bound, so a write waits about the bound plus one table, and each table reports its own outcome. A cluster server runs optimize as a recorded operation, off by default. A write that meets an optimize commit is carried over it: in a rerun on RustFS with debug builds, every write succeeded without a 409. #1275, #1282, #1349

### Keyed writes: 34 storage requests instead of 212

A one-row keyed write scanned the key column of every fragment, so its cost grew with the table. It now probes the identity index while the unindexed tail is small: at 262,144 rows in 64 fragments, an update sends 34 requests instead of 212 and an insert 18 instead of 83 (simulated store, not S3). A traversal after a write or branch change rebuilds topology only for the edge tables that changed: 26 requests instead of 59 at 131,072 edges. A `limit` with no filter reaches the Lance scanner and reads 1 of 25 data files instead of 16 on local disk. On a server, repeat commit lookups open only the branch that holds them; a hosted graph with nine branches took 13 s per lookup before, and the hosted gain is not yet measured. #1318, #1363, #1342, #1184

### Spilling queries finish within their memory budget

A correlated block that reads the outer row, such as `max($b.x) { … } > 0`, collected every inner match before folding them, so a large fan-out ran out of `query_memory_bytes`: 16,384 one-KiB inner rows were refused at 12 MiB, and now complete there (local disk). A query whose sort spilled could fail at one budget yet pass at smaller and larger ones; its merge now reserves 9.4 MiB instead of 40 at the default 150 MiB and stays within half the budget. Spill files are zstd-compressed: the whole-query spill test wrote 5.9 MB instead of 52.6 MB. #1341, #1362, #1389, #1348

## Upgrade actions

Each change closes a gap between what an operator configured and what the server allowed. A static token could read every graph that had no policy. A caller could raise its own memory and work budgets. Another local account could add a token through a writable token file. Embedded maintenance ran without a policy check. `repair` held every write lock to list commits that nothing reads. Format 17 records a branch's writer epoch, which older binaries cannot read.

- Any static bearer token could read every graph on the server that had no applied policy. Such a graph now refuses reads as it refuses every other action. Apply a policy granting `read` to each graph a token should read, or set `OMNIGRAPH_ALLOW_READS_WITHOUT_POLICY=1` on the server to keep the old behaviour. See [authentication][no-policy-reads].
- A served request could raise its own `traversal_work_limit`, `query_memory_bytes`, `write_max_bytes` or `load_source_max_bytes` without limit. A value above the server's default is now refused with a 400; operators raise the ceiling with the setting's environment variable. Lowering a budget still works. See [settings][budget-ceiling]. ([#1327](https://github.com/ModernRelay/omnigraph/pull/1327))
- Another local account that could write `OMNIGRAPH_SERVER_BEARER_TOKENS_FILE` could add a token for any actor. On Unix the server now refuses to start when that file is writable by other accounts or is not a regular file, and warns when they can read it. Run `chmod 600` on it. See [token sources][token-file-mode]. ([#1324](https://github.com/ModernRelay/omnigraph/pull/1324))
- Static bearer-token actors may no longer start with `principal:`, the prefix of signed and OIDC identities, so a server whose token configuration names one refuses to start: rename that actor and its policy rules. The AWS Secrets Manager source now also refuses duplicate token values. See [tokens][reserved-actor-prefix]. ([#1323](https://github.com/ModernRelay/omnigraph/pull/1323))
- A graph that 0.16 creates (`init`, a new cluster graph, a rebuild) is storage format 17, which 0.15.x and older refuse to open. Existing graphs stay at 16 until `omnigraph upgrade`, which has no way back. Upgrade every server and CLI that opens a graph before creating one with 0.16. See [storage upgrade][format-17-upgrade]. ([#1402](https://github.com/ModernRelay/omnigraph/pull/1402))
- Embedded hosts with a policy checker: `optimize` and `cleanup` ran unchecked. Now `optimize_as`, `ensure_indices_as`, `ensure_indices_on_as` and `rebuild_full_text_indices_on_as` need `maintain`, `cleanup_as` needs `reclaim`, and `change` admits no maintenance. The methods without an actor are removed. Grant the new actions. See [policy actions][maintenance-actions-upgrade]. ([#1275](https://github.com/ModernRelay/omnigraph/pull/1275))
- Embedded hosts: `optimize_as` takes an `OptimizeRequest` (`OptimizeRequest::default()` is a full run) and returns an `OptimizeReport` whose `tables` holds the per-table stats; `committed` is a method. `optimize --json` reports the `__manifest` row as `configuration_clear` and drops the always-null `skipped`, `published_dataset_version` and `lance_head_version`. See [bounding a run][optimize-request-upgrade]. ([#1275](https://github.com/ModernRelay/omnigraph/pull/1275))
- `omnigraph repair` and the embedded `Omnigraph::repair` report (`RepairOptions`, `RepairStats`) are removed; they only listed foreign Lance commits, which no read or write uses. A confirmed `cleanup --keep N --confirm` run, which also reclaims unretained history, lists them per table (`foreign_versions` under `--json`); embedded hosts can call the read-only `cleanup_plan`. See [foreign versions][repair-removed-foreign-versions]. ([#1372](https://github.com/ModernRelay/omnigraph/pull/1372))

## Features

- `optimize --max-gate-hold` stops starting tables once the limit passes, so writes to main wait about that long plus one table, not the whole run; `--tables` runs just those tables. See [bounding a run][optimize-bounded-runs]. ([#1275](https://github.com/ModernRelay/omnigraph/pull/1275))
- A cluster server can run `optimize` while it serves, as a recorded operation tracked by id; `omnigraph optimize` against it submits and waits. Enable with `OMNIGRAPH_OPERATION_ROUTES=true`. See [operations][recorded-optimize]. ([#1282](https://github.com/ModernRelay/omnigraph/pull/1282))
- Embedded hosts can bound, cancel and observe an optimize run through `OptimizeRequest`: table and run ceilings, an adjacency artifact limit, cancellation and a before-publish callback. ([#1275](https://github.com/ModernRelay/omnigraph/pull/1275))
- An embedded program can claim a format-17 branch (`claim_branch_writer`) so no stale process lands a write on it; other writers, server and CLI too, get 409 `writer_fenced`. See [writer epoch][writer-epoch-guide]. ([#1350](https://github.com/ModernRelay/omnigraph/pull/1350))
- Embedded hosts can open a clone (`Omnigraph::open_clone`) that reads an unchanging base graph in place and writes only to its own root, on local disk or `s3://`; `omnigraph-gqt --base` opens one. ([#1367](https://github.com/ModernRelay/omnigraph/pull/1367))
- An embedded host's query profile shows which operators spilled to scratch files and how much (`node` `spill`), and spill files are zstd-compressed to a third or a tenth of their size. See [profile][spill-profile]. ([#1348](https://github.com/ModernRelay/omnigraph/pull/1348))
- The agent skill has an [onboarding guide][skill-onboarding] that takes an agent from nothing installed to a queried, branched and merged local graph; the README's setup prompt starts there. ([#1333](https://github.com/ModernRelay/omnigraph/pull/1333))
- `omnigraph-bench run --local-route direct|object-store|read-through` compares how an engine-target repetition reaches its fixture; `read-through` opens an empty clone root over the frozen fixture. ([#1365](https://github.com/ModernRelay/omnigraph/pull/1365))

## Behavior changes

- An update, delete or overwrite load overtaken by another commit reruns once on the new head, selecting its rows again, instead of returning `read_set_conflict`; `--if-commit` refuses. See [mutations][overtaken-writes-mutations]. ([#1349](https://github.com/ModernRelay/omnigraph/pull/1349))
- `optimize` reports each table as `optimized`, `unchanged`, `deferred` or `failed`, and one table's failure no longer fails the run, so check the report for `failed` tables. See [bounding a run][optimize-run-outcomes]. ([#1275](https://github.com/ModernRelay/omnigraph/pull/1275))
- A Blob write whose branch was recreated, or whose schema changed meanwhile, returns `read_set_conflict` as other writes do, not a generic `conflict`. See [Blob writes][blob-identity-refusal]. ([#1349](https://github.com/ModernRelay/omnigraph/pull/1349))
- The installers stop on a failed download instead of switching to an edge build, which can write a format stable binaries refuse, and verify build provenance when `gh` is signed in. See [install][installer-provenance]. ([#1325](https://github.com/ModernRelay/omnigraph/pull/1325))
- The storage and embedding guides cover encryption at rest, catalog growth, the conditional writes an S3-compatible store needs (GCS is untested), and running with no outbound requests. See [storage][operator-notes]. ([#1326](https://github.com/ModernRelay/omnigraph/pull/1326))

## Fixes

- In 0.15.0 any MCP tool call, even `health`, crashed `omnigraph-server` with a stack overflow, taking every graph down, for any credential. Each tool call now runs in its own heap allocation.
- A deeply nested query, or an `and`/`or` chain past about 256 terms, crashed the server for any signed-in caller. It is now refused with `Q006` before parsing; use `in [...]` for long lists. See [parse codes][codes].
- Writes no longer stall or fail while `optimize` publishes in the same process: a write that meets an optimize commit is carried over it without preparing again. See [maintenance][carried-writes-maintenance]. ([#1349](https://github.com/ModernRelay/omnigraph/pull/1349))
- A query whose sort spills no longer fails at one memory budget yet passes at smaller and larger ones: the merge reserves less up front (9.4 MiB, not 40, by default) and stays within half the budget. ([#1389](https://github.com/ModernRelay/omnigraph/pull/1389))
- A failed storage read on the served deployment routes (`cluster apply` or `plan` against a server, deployment status) answers 503 to retry, or 500 if it repeats, not 409. See [recorded operations][recorded-operations-guide]. ([#1357](https://github.com/ModernRelay/omnigraph/pull/1357))
- The `policy` commands accept a graph bundle beside a `cluster` bundle and answer each action from the bundle a server uses for it. See [validate and test][policy-commands-by-scope]. ([#1311](https://github.com/ModernRelay/omnigraph/pull/1311))
- The container entrypoint refuses `OMNIGRAPH_TARGET_URI`, `OMNIGRAPH_CONFIG` and `OMNIGRAPH_TARGET` by name and points to `OMNIGRAPH_CLUSTER`. See [container][entrypoint-cluster]. ([#1329](https://github.com/ModernRelay/omnigraph/pull/1329))
- Upgrade `rmcp` from 3.3.0 to 3.9.0 for three RustSec advisories: an SSRF host-string check, an unbounded tool-schema cache and unbounded client response buffering. The MCP endpoint is unchanged. ([#1291](https://github.com/ModernRelay/omnigraph/pull/1291))
- Update `rustix` to 1.1.6 for [RUSTSEC-2026-0486](https://rustsec.org/advisories/RUSTSEC-2026-0486): its extended-attribute functions were unsound for a zero-length buffer. Omnigraph does not call them. ([#1350](https://github.com/ModernRelay/omnigraph/pull/1350))

## Performance

- A keyed write of a few rows (`insert`, `update ... where <key> = v`, `load --mode merge`) finds them through the identity index, not a scan: 34 requests instead of 212 at 262,144 rows (simulated store). ([#1318](https://github.com/ModernRelay/omnigraph/pull/1318))
- On a server or other long-running process, looking up one unmerged commit after another (history, review, `commit changes`) opens only the branch that holds it after the first, not every live branch. ([#1184](https://github.com/ModernRelay/omnigraph/pull/1184))
- A traversal after a write or a branch change no longer rebuilds topology for edges the change did not touch: 26 requests instead of 59 at 131,072 edges (simulated store). Results are unchanged. ([#1363](https://github.com/ModernRelay/omnigraph/pull/1363))
- A `limit` with no filter or `order` stops Lance reading ahead: `match { $p: Person } return { $p.name } limit 10` reads only the fragments holding those rows (1 of 25 files, not 16, on local disk). ([#1342](https://github.com/ModernRelay/omnigraph/pull/1342))
- A correlated block that reads the outer row, such as `max($b.x) { … } > 0`, no longer runs out of `query_memory_bytes` on a large fan-out: it folds inner matches batch by batch. Results are unchanged. ([#1341](https://github.com/ModernRelay/omnigraph/pull/1341))
- A read, diff or change page pinned to a graph commit opens that version directly instead of finding the latest first: one GET fewer on local disk, and one LIST fewer on object stores (inferred). ([#1390](https://github.com/ModernRelay/omnigraph/pull/1390))
- A reader or branch still at a table version that a write replaced reopens nothing: the cache keeps that handle until its budget (64 handles or 64 MiB) needs the room. ([#1319](https://github.com/ModernRelay/omnigraph/pull/1319))
- The next read or write after a write in the same process reuses the table versions it committed instead of reopening them, and a mutation holds the write gates for less time. ([#1291](https://github.com/ModernRelay/omnigraph/pull/1291))
- A direct `optimize` compacts a table's fragments in parallel tasks, sharing `OMNIGRAPH_MAINTENANCE_CONCURRENCY` (8) with index work; served runs and Blob tables still run one task at a time. ([#1396](https://github.com/ModernRelay/omnigraph/pull/1396))
- Filters evaluated in memory use less CPU when few rows pass: the right side of `and`/`or`, and each later condition, run only on rows not yet decided. Results are unchanged. ([#1346](https://github.com/ModernRelay/omnigraph/pull/1346))
- Export, the change feed, merges and key matching (`not`, `count` and `sum` blocks, bound edges, hash joins) use less CPU: one copy per chunk instead of two, and keys hashed a batch at a time. ([#1347](https://github.com/ModernRelay/omnigraph/pull/1347))
- `--format kv` works out its columns once per response, not once per row; against an older server that omits column names, 1,000 rows print in 0.17 s instead of 0.46 s. ([#1376](https://github.com/ModernRelay/omnigraph/pull/1376))
