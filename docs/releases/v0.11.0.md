# OmniGraph v0.11.0 (unreleased)

Notes accumulate here until the release is cut.

## Highlights

- **CLI graph errors retain their structured JSON.** With `--json`, server
  refusals preserve the error code and typed details on stdout, including
  policy denials and write resource limits. Generic failures still exit 1;
  conditional mutation mismatches still exit 4. Human diagnostics are unchanged.

- **Graph storage moves to internal manifest schema v7; v6 graphs are rebuilt
  by export and load.** Every `__manifest` registration row is now keyed by the
  manifest version that wrote it, and a branch's view of a table is the
  registration with the greatest manifest version rather than the greatest
  per-native-ref Lance version. A branch merge that adopts a source table whose
  Lance version number is at or below the target's now registers the pointer
  switch and reads the adopted rows; before, such a merge reported
  `fast_forward` and kept stale rows (lower) or failed with
  `table version N already exists ... with different state` (equal). That error
  no longer exists. The rebuild is per branch and does not carry branch
  topology, commit history or historical snapshots across; see
  [upgrade](../user/operations/upgrade.md) and
  [RFC 0062](../rfcs/0062-manifest-version-clock.md), the sole reason for this
  release's storage-format change.

- **Managed cluster creation, config upload and retirement.** `cluster create`
  requests an empty cluster, `cluster push` conditionally prepares referenced
  config files, and `cluster delete` / `cluster undo-delete` target exact
  incarnations and retained deletion operations. Durable local retry records
  preserve uncertain submissions. Bounded operation status keeps service
  progress separate from final outcomes, and normal plan/apply permissions
  still govern execution. An applied empty cluster can serve its exact
  readiness witness and empty authorized inventory before the first graph is
  added; all-failed nonempty clusters still refuse startup. See
  [managed lifecycle](../user/cli/managed-lifecycle.md).

- **Automatic graph actor nodes have been withdrawn.** Writes keep their
  existing commit attribution without creating a protected `OmniActor` table.
  Customer-defined actor types retain normal schema and data behavior, and
  plain `schema show` emits reusable `.pg` source again. The temporary
  `actor_provenance` configuration and `--actor-provenance` flags are removed.
  If you used the interim implementation, inspect stored formats before
  replacing its binary: schema IR version 3 and actor-extended cluster ledgers
  are refused, not automatically downgraded. Version-2 graphs with legacy
  ledgers need no actor migration. See the
  [withdrawal and compatibility boundary](../rfcs/0054-default-actor-provenance.md#compatibility-boundary).

- **Identity credentials leave permissions in applied policy.** Normal
  `cluster token` caches a cluster-bound identity credential with no graph or
  action grants. In a managed folder, `query` and `mutate` use it directly
  against the data endpoint, including while the control API is offline;
  applied Cedar policy decides each operation. `graphs list` discovers all
  applied graph IDs and display names, without exposing schema or storage
  metadata. Explicit server addressing uses `graphs list --discovery` for
  that minimal catalog. `--actions` with `--graph` explicitly retains the
  older restricted credential and its exact ceilings. Missing, expired, or
  unsupported credentials refuse without fallback; tokens remain in the OS
  keychain and never appear in CLI output. See
  [managed data access](../user/cli/managed-data.md).

- **Policy embedder source compatibility.** Cluster configuration authorization
  adds `PolicyAction::ConfigManage`, `PolicyResourceKind::Cluster`, and
  `PolicyEngineKind::Cluster`. External exhaustive matches on these public
  enums must add the new variants to compile. Existing static credentials,
  direct storage-holder APIs, and version-1 token structs retain their
  behavior and construction contracts; this enum expansion is still a source
  break for affected embedders.

- **Managed cluster operations from the existing CLI.** `login --api` stores
  a short-lived session in the OS keychain, and `use CLUSTER_ID --api` selects
  the Intent API for a config directory. `cluster plan`, exact saved-plan
  `apply --plan`, `status`, `history`, and `cancel` retain the API's outcomes
  and provenance, with bounded polling and idempotency keys. Malformed
  context and API failures refuse without direct fallback. Existing direct
  commands remain available without context or with explicit `--direct`;
  named-server login and operator profiles are unchanged. See the
  [managed CLI reference](../user/cli/reference.md#managed-cluster-commands).

- **Query results are rendered by Arrow's JSON writer (RFC 0051, phase 1).**
  The `rows` of `POST /query`, `POST /read`, stored-query invocation, and the
  CLI's `json`/`jsonl`/`table`/`csv`/`kv` output are now the `arrow-json`
  rendering of the result batches with the crate's default options;
  OmniGraph's own per-type cell encoder is gone. The spellings a consumer can
  observe change as follows: a null cell's key is omitted from its row (it
  was `"note":null`); `DateTime` prints as `"2024-01-01T12:34:56.789"` with
  no `Z` and no fractional part when it is zero (it was
  `"2024-01-01T12:34:56.789Z"`); `F32` scalars and `Vector(N)` cells print at
  32-bit width (`0.99`, not `0.9900000095367432`); floats in exponent form
  print as `1.0e20` and `1.0e-7` (they were `1e20` and `1e-7`), and magnitudes
  from 1e10 up or below 1e-5 take exponent form; a non-finite computed float
  prints as `null`
  (it was the string `"NaN"`). A `Date` or `DateTime` count the writer cannot
  format is refused: on load with a typed error, and on read with status 500
  and an `ErrorOutput` body naming the column, the result row, and the count.
  A store holding such a count from an earlier release fails reads and exports
  of that column, each naming the entity and the count, until the row is
  updated. Integers of every width are bare JSON numbers. In the `omnigraph-compiler` crate every `to_sdk_json` method is
  removed (the JavaScript integer mode of `QueryResult` and `RunResult`, and
  the camelCase mutation envelope of `MutationResult`), and
  `QueryResult::to_rust_json` and `QueryResult::deserialize` parse the same
  bytes, so a struct field that received `null` must be `Option` or
  `#[serde(default)]`. Rust consumers of `omnigraph-api-types` see
  `ReadOutput::rows` and `LegacyReadOutput::rows` change from
  `serde_json::Value` to `Box<serde_json::value::RawValue>`; the OpenAPI schema
  is unchanged. See [JSON result
  spelling](../user/queries/index.md#json-result-spelling).
- **Export lines, entity fetch, and change images use the same JSON writer
  (RFC 0051, phase 2).** The engine's second hand-written encoder is gone. An
  export line keeps its grammar, `{"type":…,"data":…}` and
  `{"edge":…,"from":…,"to":…,"data":…}`, and its `data` object now lists `id`
  first and the other properties in the catalog's column order (every key was
  alphabetical). Inside
  `data`: `Date` and `DateTime` are the strings above (they were raw day and
  millisecond counts; the loader reads both forms, so older files still load);
  a null cell's key is omitted; `F32` prints at 32-bit width; floats take the
  exponent form above. Entity fetch (`Omnigraph::entity_at`) follows the same
  spelling, and a `Blob` property is the `base64:`-prefixed value or the
  external URI (it was the stored descriptor object). Change-feed images
  (`before`/`after` in `POST /changes` and the CLI) take the date and float
  spellings but KEEP an explicit `null` for a null cell, because an absent key
  there means the property was not in that commit's schema.

- **`min` and `max` accept `Bool`, `Date`, and `DateTime` columns.**
  `min($p.birthdate)` over a `Date` column was refused at compile time
  (`T8: min requires numeric or string type, got Date?`), and `DateTime` and
  `Bool` columns the same way. Both aggregates now take numeric, `String`,
  `Bool` (`false` before `true`), `Date`, and `DateTime` (chronological)
  columns and return the column's own type. Lists, vectors, and Blob values
  stay refused. Over zero matched rows `min` and `max` now return a null in
  the column's own type (it was a `Float64` null); `sum` and `avg` stay
  `Float64` and `count` still returns 0. A JSON row omits the null cell's
  key, so the type shows only in the Arrow IPC result schema.

- **Repeated branch controls reuse freshly verified views.** Forking can reuse
  an already loaded source, and deletion shares its branch listing and reuses
  verified borrower views. Successful local content publication retains its
  coherent in-memory projection after lineage adoption. Stale views and failed
  handoffs keep the full reconstruction path. These changes add no persistent
  state or storage-format change; cold opens and publisher validation still
  depend on retained history.

- **Parent merges preserve snapshots inherited by child branches.** Cleanup
  and first-touch recovery check all live branch references before reclaiming
  a table fork. Previously, cleanup or a later parent write could remove a
  fork still used by a child. Merging main into a branch points each
  table that only main changed at main's history; while a child pins the
  branch's former history, the branch's next write to that table fails with `detached native
  lineage` before recovery is armed instead of destroying the child's rows.
  Create a replacement branch from the affected branch to continue writing
  while preserving existing children; merging that replacement back into the
  affected branch is refused the same way until every such child has been
  deleted. A first-touch write or merge whose target ref is a leftover no
  branch uses drops that ref before recovery is armed, on the write path as
  on the merge path, so a failure at that step never leaves a recovery
  record the next open cannot resolve.

- **Branch merge and delete use less redundant storage work.** General merges
  retain the distinction between new IDs and updates, deletion candidates use
  bounded physical-offset reads, and insert-history proofs read transactions
  without opening every historical dataset. Manifest decoding releases each
  Arrow batch after reduction. Writes to a branch other than the handle's
  current branch avoid reloading manifest history just to create commit
  metadata; merges also reuse the captured target before the fresh publication
  check. Branch deletion overlaps bounded dependency reads and table
  reclamation while retaining the existing control gates.
  A first-touch merge classifies an existing unowned target ref before arming
  recovery: one another branch still uses is refused as detached lineage, one
  a pending operation claims or whose liveness cannot be verified is refused
  as a conflict, and an orphan is dropped before the merge arms recovery, so a
  crash mid-merge never leaves a ref recovery cannot explain.
  Previously, such a ref could leave an ambiguous recovery record that
  prevented reopening the graph.
  These changes retain Lance 11 and the current graph and recovery formats.

- **Two projections producing one result column name are refused at
  compile time (`T25`).** `return { $a.num1 as number, $a.num2 as number }`
  used to run and emit two columns both named `number`; every reader that
  keys a row by column name (the JSON rows of the HTTP API, the CLI, and the
  logic-test harness) then kept only the second value, silently dropping
  the first. The check covers unaliased projections too, so `return { 1, 2 }`
  (two `literal` columns) and `return { $a, $b as a }` are refused the same
  way: give each projection its own alias.

- **A search score is a result column.** `return { $d.slug, nearest($d.vector,
  $v) as score }` returns the distance the ordering used, and `bm25($d.body,
  $q) as score` the relevance score: one computation, observed twice. The
  projected expression must repeat the leading `order` key (`T33`); without
  an alias the column is `d._distance` or `d._score` (`Float32`, Lance's
  precision). Before, the spelling passed `lint` and typecheck, then failed at
  execution with `unsupported projection expression: Nearest { … }`, so the
  user docs advertised a column that never existed. Still refused, now at
  compile time with their own codes: a rank expression under an aggregate
  (`max(nearest(...))`, `T32`), a search predicate in `return` (`search`,
  `fuzzy`, `match_text`, `T35`), an alias projected a second time
  (`$d.slug as s, s as t`, `T36`), and `rrf(...)` in `return` (`T37`, until
  the fused score becomes a column).

- **`return { $p }` returns the node, not its id.** A bare node variable in
  the return list used to project only the node's `id` as a string, while
  `lint --json` described the field as an `object`. It now returns one object
  per row: the `id` and every property except `Blob` and `Vector` ones
  (`{"id": "alice", "name": "alice", "age": 30}`). Project a property
  (`$p.name`, `$p.embedding`) for a single field. `count($p)` is unchanged;
  a query that groups by `$p` now shows the object in that column;
  `sum`/`avg`/`min`/`max` over a bare node binding are refused at compile
  time (`T8`) instead of returning the smallest or largest id.

- **A self-loop no longer makes a hop range starting above 1 report a node
  one hop late.** `$a knows{2,2} $b` on `a->b, b->b` returned b, which is one
  hop from a, because a self-edge on a node already reached was emitted as a
  destination one hop later. Hop counts are shortest-path distances: only
  the start node's own self-loop counts, as one hop. Ranges starting at 1
  are unchanged.

- **A JSONL load refuses a `Date` or `DateTime` value of the wrong JSON
  type.** `omnigraph load` and `POST /graphs/{id}/load` (and the deprecated
  `ingest` aliases over the same loader) stored NULL for a nullable date
  property whose value was a float (`19723.0`), a boolean, or an object, and
  reported success; the same row through `POST /graphs/{id}/load/ndjson` was
  refused. Both paths now fail the load with `invalid Date value 19723.0 for
  property 'since': expected an integer day count or a date string` (or the
  `DateTime` equivalent), for scalars and list items alike, nullable or not. A whole-number float such as `19723.0`
  is a float to the loader; send the integer. Integer counts, `YYYY-MM-DD`
  strings, and `null` load as before. Fixes #628.

- **A `Date` string with a time of day is refused.** A `Date` value given as
  a datetime string was parsed as an instant and its UTC calendar day was
  kept: `"2024-01-01T02:00:00+05:00"` was stored, and compared in filters,
  as `2023-12-31`. A load row, a mutation or query param, a `date(...)`
  literal, and a `Date` bound through the Rust `ParamMap` API now all refuse
  any such string, including `"2024-01-01T00:00:00Z"`, with `invalid Date
  literal '…': a Date is a calendar day (YYYY-MM-DD); a string with a time of
  day belongs in a DateTime`. A value bound to a `Date` parameter through the
  Rust `ParamMap` API must now be a `Date` literal (a `String` or `Integer`
  there used to reach the comparison cast). Integer day counts and the
  day-only spellings arrow accepted before (`2024-01-01`, `20240101`, signed
  extended years) are unchanged; an instant belongs in a `DateTime` property.
  Fixes #671.

- **Branch merges no longer fail on an unrelated wide row.** The ordered
  merge cursors (the general three-way walk, the adopt fallback, the
  lineage-candidate fetch, and the Blob-selection passes) now sort only the
  row key (`id` plus row identity) and hydrate complete rows through bounded
  row-address reads afterward, so payload columns never pass through the
  sort's 37.5 MiB single-row hard cap. In v0.10 a merge with a tiny edit
  could fail with `resource limit exceeded for ordered_scan_input_batch_bytes:
  actual 39321601, limit 39321600` because an untouched pre-existing row
  (for example one written by an overwrite load, which is exempt from the
  keyed 32 MiB row envelope) was sorted at full width; the reported `actual`
  was a fixed sentinel, not a measurement. Rows that are part of the merge
  delta remain subject to the existing 32 MiB staging envelope. When an
  ordered scan does hit a resource limit, the error now carries the byte
  count actually measured and names the affected table and snapshot role
  (`base`, `source`, or `target`); the `limit + 1` sentinel survives only
  when the upstream message cannot be parsed. Merge results and conflict
  classifications are unchanged; ordered-by-`id` exports and the change feed
  keep v0.10's full-row sort and its row-width limit.

- **Two branches that merged the same third branch no longer report a false
  `divergent_update`.** A merge commit names its merged parent by id, but
  that commit's record lives in the branch it was merged from, and the
  merge-base walk read only the two merging branches' lineage. After `x` was
  merged into both `s` and `t`, a merge of `s` into `t` stopped at `x`'s
  commit, took the older fork point as the base, and saw `x`'s change as an
  edit on both sides: an entity `t` then changed and `s` did not was refused
  with `merge conflicts: … (divergent_update)`. The walk now reads the
  missing records from the other live branches, so the shared import is the
  base and only the edits after it are compared. A commit no live branch
  holds (its branch was deleted and no branch forked from it remains) still
  leaves the walk at the older base, with a warning in the server log naming
  the commit when both merging branches descend from it.

- **Repeated variables and anonymous endpoints no longer collide in the
  executor.** Three typechecker-legal shapes (`$p knows $_` twice, `$p:
  Person` bound twice at the top level or inside `not { }`, and `$p knows
  $p` twice) handed the executor two producers of one column: a debug build
  panicked at `hconcat_batches: duplicate column`, and a release build ran
  the second binding as a cross join over a silently shadowed column. Each
  `$_` now gets its own column, a second binding of a bound variable becomes
  a constraint on the existing rows, and the compiler refuses any plan that
  would introduce a variable twice. A variable introduced by a traversal
  and then bound twice with property matches (`$p knows $f  $f: Person {
  age: 40 }  $f: Person { name: "x" }`) keeps both sets of matches; before,
  the second replaced the first. A variable rebound inside
  `not { }` that is not the root of its inner pattern kept none of its
  property matches before; it keeps them now. Variable names beginning with
  `__` are reserved. Fixes #605.

- **Adaptive traversals with a persisted adjacency index.** The traversal
  cost decision now reruns at every hop with the observed frontier, and a
  traversal that outgrows the indexed path switches to the in-memory CSR
  mid-flight, carrying its state. `optimize` additionally persists the built
  adjacency as a new object under the graph root
  (`__graph_index/csr-current.bin` — derived and regenerable; every load is
  verified and falls back to the in-memory build), so cold traversal builds
  load one object instead of scanning every edge dataset; the artifact is
  refreshed by edge-committing `optimize` runs. An unordered, aggregate-free
  `limit n` on a trailing traversal now stops at the cap: it returns any
  valid `n` rows (a subset, not a slice), so which rows you get for such
  queries can change from v0.10.
- **Search-ordered results are ranked by score, deterministically.**
  `order { nearest(...) }` / `bm25(...)` results are now explicitly sorted on
  the search score (ascending distance / descending relevance) with the
  documented entity-id tie-break, including through multi-hop traversals, and
  keys after the search function apply as secondary sorts. Observable result
  order can change on upgrade where scores tie (previously the storage
  engine's internal order leaked through), and `order … limit n` now runs a
  bounded top-k sort. `_distance` and `_score` become reserved property names
  for NEW schema declarations (existing graphs that already declared them
  keep opening).
- **Edge keys: derived edge identity (RFC 0044).** An edge type may declare
  `@key(src, dst, ...)`; keyed edge inserts derive their row id from the key,
  so the same relationship inserted on two branches converges on merge (or
  surfaces `divergent_insert` when non-key properties differ) instead of
  silently duplicating. A schema that declares an edge key is stamped with a
  new `ir_version`; unkeyed schemas keep the current number and existing
  graphs are unaffected. Property names `id`, `src`, `dst`, `from`, and `to`
  are now refused on new edge declarations — they shadow physical columns
  or endpoint parameters.
- **Bounded ranked full-text scans.** A `bm25()` ordering with a `limit` now
  reads only the top-scoring matches (a small multiple of the limit) instead
  of hydrating every matching entity. This fixes ranked reads with traversals
  failing at corpus scale with an Arrow offset overflow (#563) and makes
  join-free ranked reads proportionally faster. When traversals or filters
  leave the limit unfilled, the query automatically rescans without the
  bound, so result sets are never truncated; aggregate returns are never
  bounded. Full-text rankings inside `rrf()` are not bounded: bounding an
  arm could silently shift fused results when a traversal drops its top
  matches, so each full-text arm still scans every matching entity. `rrf()`
  answers are unchanged from v0.10. Its cost is unchanged only in the broad
  regime: an `rrf()` ranked read without a selective traversal still
  hydrates its full matched corpus per full-text arm, keeping v0.10's cost
  and, with traversals, v0.10's Arrow offset-overflow exposure (#563 is
  fixed for `bm25()` orderings; the selective-traversal prefilter below
  removes both at small eligible sets). A `nearest()` ranking inside
  `rrf()` remains top-k, as vector search always is: an entity outside its
  window contributes no vector rank to the fusion.
- **Selective `rrf()` reads prefilter their full-text arms.** When a
  traversal constrains the ranked variable and the graph index shows few
  entities could survive it, each full-text arm now ranks only those
  entities — an `id` scalar-index prefilter pushed into the scan — instead
  of the whole matched corpus. The two plans return identical results (up
  to equal-score ties): the eligible set always over-approximates the
  traversal's survivors, the arms stay unbounded, prefiltered plans are
  admitted only while the full-text index covers every fragment, and
  `nearest()` arms run identical code either way. The choice is therefore
  pure cost: selective ranked reads with traversals stop paying
  corpus-scale scans (and, at #563 scale, stop overflowing), while broad
  reads keep the exhaustive path. `OMNIGRAPH_RRF_PLAN` forces either plan
  for diagnosis (a forced prefilter still respects the correctness
  admission checks and falls back rather than change results);
  `OMNIGRAPH_RRF_GATE_RATIO` / `OMNIGRAPH_RRF_GATE_MAX_IDS` tune the
  threshold.
- **Bounded `nearest()` probing with exact widening.** An IVF `nearest`
  scan reads at most 20 payload partitions per index delta
  (`OMNIGRAPH_ANN_NPROBES`; `0` removes the cap), so Lance's
  centroid-distance heuristic no longer expands a small search across the
  whole index (#567). A capped scan that comes back short with partitions
  unread is rerun at four times the cap, then uncapped, and is never rerun
  when it ended short for another reason: fewer matching rows than requested,
  or the whole type read. A `nearest` query left short of `limit` by a
  traversal or a filter above the scan asks for four, then sixteen times the
  candidates instead of rerunning the scan uncapped (#665: the earlier retry
  lifted the cap but kept the candidate count, so such queries returned the
  same short answer after a whole-index read); survivors rarer than one in
  sixteen candidates are found by one exact pass over the whole type, so
  `limit` is filled whenever that many survivors exist. A traversal-constrained
  `nearest` with few eligible entities ranks only those entities, through the
  same selective-read gate as `rrf()` above, and an eligible set proven empty
  runs no scan. `nearest()` arms inside `rrf()` keep their top-k window and
  widen only their own cap. Search scans read only the columns the query
  needs plus Lance's ranking column; the vector column is read only when
  returned.

- **Warm queries skip repeated catalog builds, compiles, and full-text
  checks.** The accepted catalog is memoized on the schema contract's exact
  bytes: the bytes are still read on every query, so a schema apply by
  another handle is observed on the next query and any drift still fails
  validation, but an unchanged contract no longer rebuilds the catalog.
  Named queries are compiled once per source digest, query name, and catalog
  build (256 entries per handle; errors are never cached). A scan with no
  full-text query, no SQL-string filter and no `contains_tokens` demand in its
  typed filters skips the full-text index validation.

- **Branch operations are writable as GQ statements.** A `.gq` file may hold
  exactly one branch statement instead of query declarations, a third
  top-level form beside read and mutation declarations: `branch create <name>
  [from <parent>]`, `branch delete <name>`, `branch merge <source> [into
  <target>]`, and `branch list`. The three control writes are served by
  `POST /mutate` and `branch list` by `POST /query`, in the existing request
  and response envelopes, with a merge reporting its result in the new
  optional `ChangeOutput.outcome`. The CLI's `mutate` and `query` verbs accept
  a statement file, and `.gqt` steps take a `branch:` argument and an
  `outcome:` expect mode. Where query declarations are expected the statement
  is refused by name: `lint`, `cluster validate`, and stored-query load each
  reject a statement file, and on the data routes the parse error now precedes
  the policy denial. See [RFC
  0055](../rfcs/0055-gq-branch-statements.md).

## Cluster configuration

- **`..` segments and symbolic links in declared relative paths are
  refused.** A relative schema, query, or policy path in `cluster.yaml` that
  contains a `..` segment now fails validation with `config_path_escape`,
  and one that reaches its file through a symbolic link, on the way to it or
  as a discovered query file, fails with `config_path_symlink`, each naming
  the setting that declared it. A bundle is one directory of files read
  exactly as declared. Absolute paths keep their old behavior: they are
  accepted as given and are not checked for either shape.

## Cluster operations

- **Observe without the lock.** `cluster observe` reports what `refresh`
  would record (catalog payload findings and live graph observations)
  without taking `__cluster/lock.json`, running the recovery sweep, or
  writing the ledger, and `cluster plan --observe` plans the same way. Both
  outputs carry `authority: "observed"` and the exact `state_cas` they read;
  an existing lock is reported, not refused (RFC 0049).
- **Honest authority and a bounded revision.** Every `plan`, `refresh`, and
  `import` output now carries `authority`: `locked`, `observed`, or
  `unlocked` when the bundle sets `state.lock: false`. `refresh` refuses with
  `state_revision_overflow` instead of silently staying at `u64::MAX`, and
  the human output distinguishes a lock this command acquired from one
  another process holds (RFC 0049).

## Server

- **Offline signed credentials with separate profiles.** `--data-token-trust`
  binds public P-256 keys to the server's actual cluster root and identity
  before graph open. Identity credentials authenticate an immutable principal;
  applied Cedar policy supplies permissions, including schema authorization
  through the cluster configuration owner. Legacy restricted credentials keep
  their graph/action ceilings and schema exclusions. The additive
  `GET /graphs/discovery` exposes graph IDs and display names to every valid
  identity credential; `GET /graphs` retains its protected metadata contract.
  Verification needs no issuer connection. Existing static credentials retain
  their behavior and can coexist for recovery. See
  [signed data credentials](../user/operations/server.md#signed-data-credentials).
- **Readiness witness.** `GET /readyz` reports whether a replica is serving
  or draining, the applied `config_digest` it booted from
  (`booted_serving_digest`), the ledger revision and CAS it read, and how
  many applied graphs it serves and does not serve; it answers 503 once
  shutdown has begun. It is unauthenticated and names no graph: the
  authenticated `GET /graphs` gains `quarantined`, the applied graphs this
  process does not serve. `/healthz` is unchanged (RFC 0049).
- **Bounded shutdown.** `--shutdown-grace-seconds` (else
  `OMNIGRAPH_SHUTDOWN_GRACE_SECONDS`, else 25) puts one deadline on graceful
  shutdown: readiness turns off at the signal, in-flight requests drain, and
  at the deadline a watchdog thread exits the process with status 2 and the
  unfinished work logged, whether or not the async runtime is still making
  progress. The signal is handled from process start, so the bound covers
  startup. A clean drain still exits 0. Set the orchestrator's termination
  grace longer than this value (RFC 0049).
