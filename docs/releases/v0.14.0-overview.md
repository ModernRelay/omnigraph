# OmniGraph v0.14.0: highlights and upgrade actions

Released 2026-10-22.

0.14 redesigns the CLI for consistent destination selection and configuration.
It also brings MCP access through the existing server, branch review and deferred
publication, and parallel CSV imports. HTTP,
MCP tool results, and CLI failures now describe whether an operation had effects
and what the caller should do next.

This overview describes the **final 0.14.0 release**. The
[complete changelog](v0.14.0.md) preserves all individual change notes, including
intermediate designs superseded during development. Follow the current
[0.13 → 0.14 checklist](../user/operations/upgrade-0.14.md) for the ordered
upgrade procedure, before/after YAML, and command replacements.

## Highlights

### A CLI redesigned for consistency

Data and deployment commands select their destination with `--target`, or the
configured `defaults.target`. Named targets bind a local graph/root, server, or
managed cluster to its access settings. Commands reject incompatible targets
and invalid selections without falling back to folder context; backend mutations
print the resolved destination before execution.

Control-plane identity has a separate home: `profiles` and `--profile` select
the managed API, organization, and identity. `--config DIR` selects the local
`cluster.yaml` source bundle. Credentials belong to an explicit target or
profile, and `defaults.target` and `defaults.profile` are independent.

This replaces overlapping routing flags and implicit selection while retaining
the existing command families and declarative plan/apply workflow. Old resource
profiles become targets; the new profiles have a different purpose. There is
no automatic configuration importer. See the
[YAML and CLI migration examples](../user/operations/upgrade-0.14.md).

### Agent access through the existing server

Servers with configured bearer credentials expose `/mcp` using the same graph access, request
handlers, and authorization policies as their HTTP API. A stdio client can
connect through the CLI without receiving the server's token:

```bash
omnigraph mcp --target production --graph knowledge
```

`production` must be a configured server target. Write tools require the
server's `--mcp-allow-writes`; a stdio bridge also requires `--write`. Ad-hoc
reads have their own server opt-in, `--mcp-allow-adhoc`. See the
[MCP guide](../user/operations/mcp.md) for setup, tools, limits, and error handling.
No second serving process or local embedded server is introduced.

### Review branches before merging

Use `branch diff` to review a branch against its merge base, or `diff` to compare
explicit branch or commit positions. Inspect the common ancestor with
`branch merge-base`, and preview a merge without publishing it:

```bash
omnigraph branch merge feature --into main --dry-run --target production
```

`branch create --from-commit` can start work at a retained published commit
under the current schema. These operations use graph commits across tables. See [branch review](../user/branching/changes.md) and
[merge previews](../user/branching/merge.md).

### Prepare a change before publishing it

A mutation or merge ending in `as commit` produces an unpublished result that
can be inspected by commit ID before `commit publish` moves the target branch.
`commit drop` discards it. `as unattached branch` instead creates an inspectable
snapshot that can be extended but never published.

Both depend on the captured target branch remaining unchanged. Advancing or
replacing that branch expires the pending result; it is not a durable approval
queue. Review and publish against the same branch head. See
[unpublished commits](../user/branching/index.md#unpublished-commits) and
[unattached branches](../user/branching/index.md#unattached-branches).

### Parallel CSV imports and richer query results

GQ `load csv` imports a schema-typed node or edge source through `mutate`.
Overwrite imports can parse and stage data in parallel while preserving a
single graph publication. `explain` describes a load before execution. See
[CSV loading](../user/mutations/index.md#csv-loading) and
[explaining a load](../user/queries/explain-load.md).

Queries also gain `return distinct`, `count(distinct ...)`, and Boolean
comparisons over aggregates. Search diagnostics expose native ANN work in the
same query's execution report. See [queries](../user/queries/index.md) and
[explain](../user/queries/explain.md).

The development CSV measurements show improvements for the measured workloads;
throughput still depends on the input, hardware, storage, and operation. This
release does not promise a fixed time for an arbitrary row count.

### Failures describe effects and recovery

OmniGraph API errors include a stable `code` and a `disposition` describing
effects and the next action. MCP tool execution failures carry that API error
body; MCP protocol errors have their own shape. Single data-write CLI commands use the same
classification to select an exit status. An uncertain write must be reconciled,
not blindly submitted again. See [failure handling](../user/operations/troubleshooting.md#failed-data-write-commands).

## Upgrade actions

Follow the [0.13 → 0.14 checklist](../user/operations/upgrade-0.14.md) in order.
The sections below summarize the affected contracts and link to their owners.

### 1. Coordinate the fleet and preserve rollback

Stop application traffic and old processes. Verify a backup of the **whole
cluster storage root** for a cluster, including `__cluster/` and every graph,
or the **whole graph root** for a standalone graph. Preserve history, indexes,
branch references, and deployment state; keep the old executables. Upgrade the CLI, server, and integrations
together. Do not run mixed old and new writers against one root.

The released 0.13 binary writes graph format 14. The released 0.14 binary serves
formats 14–16 and writes format 16; an ordinary publication advances its branch
to 16. Existing 0.13 graphs need no export/rebuild merely for this transition.
Explicit stamping for operations that require a newer format, and migration
from older graphs, follow the [upgrade guide](../user/operations/upgrade.md).

0.14 uses Lance 13. Certified Lance 11 full-text indexes remain compatible;
uncertified or incompatible indexes still require explicit rebuilding. Neither
unchanged data-file encoding nor a passing read qualifies arbitrary rollback
after new writes: restore the verified pre-upgrade backup for rollback.

### 2. Rebuild operator configuration using the final CLI model

The new configuration document uses `version: 1`, with two distinct kinds of
entry:

- `profiles` select a control-plane endpoint and identity. Use `--profile` for
  login, organization management, and cluster discovery or creation.
- `targets` select a resource: a local graph/root, a standalone server, or a
  managed cluster. Use `--target` for data and deployment operations. A managed
  target refers to its profile; a standalone server target has its own `auth`.

The defaults are independent: `defaults.profile` and `defaults.target`.
`--config DIR` names a local directory containing `cluster.yaml`; it does not
select the destination. For a **self-hosted server target** named `production`:

```bash
omnigraph cluster validate --config ./company-brain
omnigraph cluster plan --target production --config ./company-brain
omnigraph cluster apply --target production --config ./company-brain
```

Managed deployment uses `cluster push`, then `cluster plan --rev`, then
`cluster apply --plan` against a managed target; it does not use the server
source-apply sequence above. See the
[before/after commands](../user/operations/upgrade-0.14.md#replace-cli-invocations).

Old routing flags and folder context are rejected. There is **no automatic
importer**. Recreate configuration using the
[before/after YAML](../user/operations/upgrade-0.14.md#rebuild-operator-configuration).
Settle pending work with the originating build before migration: normal 0.13
folder journals cannot be imported by `config recover-operations`. Preserve the
old operator home and journals; see
[recovery compatibility](../user/cli/targets.md#upgrade-from-the-old-format).
Create a new managed profile with `login --create-profile NAME`; plain `login`
uses an existing selected profile. Install a standalone target's token with
`credentials set --target NAME --stdin`, or declare an explicit credential
source. `OMNIGRAPH_BEARER_TOKEN` and implicit per-name token variables no longer
select credentials.

### 3. Update HTTP, MCP, and script consumers

HTTP requests require `Omnigraph-Http-Api: 0.14`. Regenerate clients from the
release's OpenAPI and update renamed paths, parameters, operation IDs, and
DTO fields. The same header was used by some earlier development builds, so
it does not prove those builds implement the final release's shapes.

Check these consumers in particular:

| Consumer | Required action |
|---|---|
| Actor and load receipts | Read `actor_id`; `load --json` no longer returns `uri`, and includes `base_branch` |
| Commit listing | Use `listing=` instead of the retired `unpublished` / `unattached` booleans |
| HTTP error handlers | Read `code` and `disposition`; failed Blob `If-Match` is `412 precondition_failed` |
| Single data-write CLI error handlers | Replace `command_outcome` with `disposition`; exit 2 means partial/unknown effects, 1 a no-effect failure, 4 a failed condition, 64 parser refusal, and 75 busy. Other command families have their own exit behavior |
| Served actor assertions | `--as` now sends `Omnigraph-If-Actor`; a match permits execution and a mismatch refuses it before effects |
| MCP clients | Refresh cached tool schemas and handle tool failures as an `error` body with an optional HTTP `status`; MCP and OAuth have their own protocol negotiation |
| Saved plans and explain readers | Regenerate saved plans for bound-plan version **10** and parse explain version **7** |

For details, see the [HTTP contract](../user/operations/server.md#http-contract),
[CLI output reference](../user/cli/reference.md#machine-readable-read-and-write-positions),
and [explain guide](../user/queries/explain.md).

**npm availability:** `@modernrelay/omnigraph@0.14.0` and
`@modernrelay/omnigraph-mcp@0.14.0` are published. Upgrade the SDK alongside the
server; their 0.13.0 packages are incompatible with a 0.14 server. See
[client compatibility](../user/install.md#client-compatibility).

### 4. Check affected schemas and application data

- Full-text functions on String properties now require `@index`; declarations
  without it fail type checking. Review and validate stored queries before
  deploying. See [search](../user/search/index.md).
- Offline embeddings made by the earlier `omnigraph embed` text concatenation
  need regeneration with `--reembed-all` and reloading. Each embedding spec
  must name the single source field declared by `@embed`. See
  [offline embeddings](../user/search/embeddings.md#offline-file-pipeline).
- Recheck `@range` declarations before reapplying schemas: an upper-only bound
  is inclusive, oversized integer bounds are rejected, and list ranges apply
  to each element on writes. Existing rows are not retroactively rewritten.
  See [constraints](../user/schema/index.md#constraints).
- Send branch names exactly. Leading/trailing whitespace and control characters
  are rejected rather than trimmed. See [branch names](../user/branching/index.md#branch-names).

Verify representative reads, writes, searches, policy decisions, and client
error handling before restoring traffic. Azure remains a qualification preview;
its writer-admission requirements still apply.
