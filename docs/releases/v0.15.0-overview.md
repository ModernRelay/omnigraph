# Omnigraph v0.15.0: what changed and what it means for you

Released 2026-11-09.

Omnigraph 0.15:

- loads a large dataset into a new graph in less than half the time 0.14 took;
- keeps reads from waiting for writes to commit;
- makes most branch diffs and merges cost what changed, not how big the
  tables are or how long the history is;
- closes three ways in which two servers could write to one S3 cluster at once;
- gives MCP agents every graph operation, under your Cedar policy;
- lets `schema apply` make a property required, or add `@unique`, on a type
  that already has rows, without a rebuild.

Act before you upgrade if any of these is true:

- You serve MCP. Agents will be able to call every tool that their policy
  allows, writes included, even if you never set an MCP flag.
- Your schema has a `@card` minimum, such as `@card(1..)`, and you load nodes
  and their edges in separate steps.
- Your schema has `@unique` on a list or vector property.
- You manage a managed organization's members with scripts.
- You embed the Rust engine and save query plans or build publication errors.

[Before you upgrade](#before-you-upgrade) says what to do in each case. Graph
storage does not change, and existing graphs open without a rebuild.

This page explains the release. The [complete changelog](v0.15.0.md) lists
every change with its pull request.

## Before you upgrade

### You serve MCP from `omnigraph-server`

After the upgrade, every agent can call every MCP tool that its credential's
policy allows, writes included. This is true even if you never set an MCP
flag. In 0.14, write tools were hidden unless the server ran with
`--mcp-allow-writes`, and ad-hoc queries unless it ran with
`--mcp-allow-adhoc`.

Why: the flags hid MCP tools from a credential that could already make the same
calls over HTTP, and agents reported the hidden operations as missing
features. 0.15 keeps one gate, your Cedar policy, so an agent can do over MCP
what its credential can do over HTTP.

What to do, before you upgrade:

1. Check the policy of every credential that an agent uses. A static token on a
   graph with no policy can only read, so it stays read-only.
2. If an agent must stay read-only, narrow its policy. If the agent shares its
   credential with a person or a service, give the agent its own credential
   first, so that narrowing it does not restrict them too. An agent that signs
   in through OIDC acts as the person who signed in, and has that person's
   policy.
3. Remove `--mcp-allow-adhoc` and `--mcp-allow-writes`: a server started with
   either flag refuses to start. `OMNIGRAPH_MCP_ALLOW_*` environment variables
   are ignored, with no warning.
4. Replace calls to the `read` tool with `query`, which takes GQ source or a
   stored query's `name`. Then refresh the agent's tool list.

See [MCP settings](../user/operations/mcp.md#settings). #1207

### Your schema has a `@card` minimum

An edge type such as `WorksAt: Person -> Company @card(1..)` says that every
`Person` has at least one `WorksAt` edge. 0.14 checked this rule on some writes
and not others: it let you insert a person with no employer, but refused to
delete a person's last employer. So a graph could hold nodes that break the
rule its own schema declares. 0.15 checks the rule on every write that inserts
or updates a person, and refuses the write with
`@card violation on edge WorksAt: source '…' has 0 edges (min 1)`.

What this means for you:

- A new person must arrive in the same write as its edges: one mutation query
  that inserts both, or one JSONL load (`omnigraph load`) that carries both.
  `load csv` cannot add nodes to such a type, because a node CSV has no edges.
  So an import that loads `person.csv`, then `works_at.csv`, is refused at its
  first step. Edge CSVs for people who already exist still load.
- A person who already breaks the rule is refused the next time any write
  updates it, even one that only changes a property. A rebuild from an export
  refuses it too.
- Schema apply refuses a new edge type with a minimum on a node type that
  already exists (`OG-MF-107`), because the existing nodes have none of the new
  edges. Add such an edge type without a minimum.

What to do, before you upgrade: find the nodes below the minimum and add their
edges. A query that matches each `Person` with `not { $p worksAt $c }` lists
them; [edge cardinality](../user/schema/index.md#edge-cardinality) has it in
full. Then move imports for these types from `load csv` to JSONL or to
mutation queries. #1212

### Your schema has `@unique` on a list or vector property

0.14 accepted `@unique` on a list or vector property, but every write that gave
the property a value failed, so these properties hold no values. 0.15 refuses
the declaration.

What this means for you: the graph still opens, reads and exports. But a schema
apply whose source keeps the constraint is refused. In a cluster, that refuses
every `cluster apply` of the deployment, even one that changes only another
graph, a stored query or a policy, until you remove the constraint.

What to do, before or after you upgrade: apply one schema change that drops the
properties the constraint names, then a second that adds them back without
`@unique`. Because these properties hold no values, dropping them loses
nothing. If the constraint also names another property or an edge endpoint,
Omnigraph cannot remove it in place: export the graph and load it into a new
graph with the corrected schema. A new graph does not keep the old commit
history. See [constraints](../user/schema/index.md#constraints). #1306

### You manage a managed organization's members

Organization permissions now come from each member's roles in your identity
provider, and graph and deployment access come from the cluster's Cedar
policy. The local grants that `organization members apply` edited no longer
exist, so scripts that call it stop working.

What to do:

- Replace `organization members apply` with
  `organization members set <email> --role <role>`. Repeat `--role` for every
  role the member keeps: the command replaces the member's whole set of roles.
- Add `--role` to `organization invitations send`.
- Offboard with `organization members offboard <email or user ID>`, without
  `--expected-version`.

See [team administration](../user/cli/managed-team.md). #1200, #1179

### You embed the Rust engine

The CLI and the HTTP API are not affected by these two changes.

- A bound plan saved with `Executed::replay_envelope`, to replay later with
  `Session::replay_bound_plan`, now uses envelope version 11, which can carry a
  `U64` parameter above `i64::MAX`. 0.15 refuses older saved plans and tells
  you to regenerate them, and older binaries refuse version 11. Regenerate
  saved plans after you upgrade. See
  [saved plans](../user/queries/explain.md#profile). #1102
- When Omnigraph cannot tell whether a commit was published, for example
  because a storage answer was lost, its error now names that graph commit, so
  you can check whether it landed. Code that builds this error with
  `OmniError::manifest_publish_in_doubt` must pass the commit ID. Code that
  reads it uses `is_manifest_publish_in_doubt()` and `publication_id()`: the
  `ManifestError.publication_in_doubt` field changed from `bool` to
  `Option<Box<String>>`. Server logs name the commit in a `publication` field.
  See the [error API](../user/operations/storage-failures.md#rust-error-api).
  #1124

### Smaller things to check

- OIDC clients: an identity the server has not admitted now gets 403
  `not_admitted` instead of 401, and an expired admission snapshot gets 503
  with `Retry-After`. A client that signed in again on every 401 looped; it
  now gets an answer it can report. A client that decodes the error `code`
  against 0.14's list of codes cannot parse `not_admitted`. #1185
- `omnigraph rebuild-full-text-indexes` is now
  `omnigraph index rebuild --kind full-text`. The old name still works in this
  release and prints a warning. Update runbooks before it is removed. #1150
- An overwrite `load csv` into a type with a `@key` now reserves its memory
  before it reads, so a load close to `query_memory_bytes` may need a higher
  limit. The refusal names the smallest limit that would admit the load. #1187
- An overwrite `load csv` refuses a file whose first record (its header line,
  or its first row) is longer than 8 MiB. #1158
- A mutation `where` in which more than four properties are each tested twice
  or more with `=`, `!=` or `in` is refused before it changes anything. This
  comes with the fix for [null rows](#wrong-results-fixed). #1286
- To go back to 0.14 after a sign-in with 0.15, log out with 0.15 first:
  older binaries refuse the new 30-day login cache. #1199

## What you get

### Bulk loads into a new graph in under half the time

An initial import, or a rebuild from an export, now takes less than half the
time it took in 0.14. In local runs of the LDBC SNB SF30 dataset (34 GB of
CSV, 31 load statements into a new graph, release builds on an Apple silicon
workstation with local disk), the load took 261 seconds on 0.14.0 and between
87 and 110 seconds on 0.15. Loads from S3 were not measured.

`load csv` in `overwrite` mode now works as a pipeline. Each parse thread reads
its own 8 MiB pieces of the source, checks keys and edge endpoints as rows
arrive, and writes data files while the next rows parse. Checks that a new
graph cannot fail are skipped. A refused load still leaves nothing behind. Most
of the gain is for `overwrite` loads: `append` and `merge` still read the whole
source before they parse it. #1141, #1147, #1158, #1178

Appends and merges into large tables also stop running out of memory. In 0.14,
a key check could send Lance a filter that listed every key in the load, and
Lance copied it into its plan for every data file. One report measured 7 to 11
GB per load, and a process killed in a 24 GB container. 0.15 reads the key
column once instead. #1231

### Reads no longer wait for writes

Within one server process, a read that arrived while a write was committing
waited for the commit, because the commit held a lock across a storage round
trip. On S3 that round trip is a network request. In 0.15 a read never waits
for a write in the same process. #1228

Writes wait less too. A write that touches several tables, such as a node type
and its edges, commits them in parallel: two round trips at commit, where it
used to take two for each table. So the next write on that branch starts
sooner. The first read after another process commits sends 11 or 12 storage
requests, where it sent 18 to 20. #1270, #1230

How it works: the graph's current state is an immutable value behind an atomic
pointer. A read takes the pointer. A write builds a new value and swaps the
pointer in one step.

### Diffs and merges cost what changed

Reviewing or merging a branch used to cost more the larger the table and the
longer its history. A diff read every row of every type that changed. A merge
read every data file of each table, and a table that many small commits wrote
has many data files.

In 0.15 most diffs and merges read only what changed:

| Case | 0.14 | 0.15 |
|---|---|---|
| Diff of ten updated rows in a type with 100,000 rows | 277 requests, 6.9 MB | 14 requests, 27 KB |
| The same diff with 4,000 rows | 17 requests, 287 KB | 14 requests, 27 KB |
| Fast-forward merge after 1,024 one-row commits | 4,168 requests | 54 requests |
| Three-way merge after 1,024 one-row commits | 3,216 requests | 135 requests |

These counts come from Omnigraph's simulated store, which runs in memory and
counts every storage request. On S3, each request is a network round trip.
#1201, #1229, #1301

This covers a branch review (`branch diff`) and a diff along one line of
history. A diff between two branches that have both moved, a review of a
branch that merged its parent back in, and a merge of a table with Blob
properties still compare everything.

How it works: Lance keeps a stable ID for each row and records the version
that last wrote it. Omnigraph pairs rows by ID and reads only the ones whose
version differs.

### Agents get every graph operation over MCP

MCP now has a tool for every graph operation except byte streams (Blob
payloads and exports). An agent can review a branch diff, find a merge base,
publish or drop a commit proposed with `as commit`, and run a stored mutation.
It could do none of these over MCP in 0.14. Each tool runs the HTTP route's
code under the same policy action, so it returns the same answers and
refusals. #1139, #1207

Search results also say how to read their scores. A read ordered by `nearest`,
`bm25` or `rrf()` returns a `ranking` object: which search ranked the rows,
whether a higher or a lower score is better, which columns hold the scores,
and whether the search was exhaustive. `exhaustive: false` means that a vector
search skipped part of its index, so a nearer row may exist. #1130

### S3 clusters: no second writer after a pause

An S3 cluster lets one server write at a time, under a lease that the server
renews every 10 seconds (the lease is 30 seconds by default). Before 0.15,
three gaps could leave two servers writing to the same cluster:

- A server paused past its lease, by a stalled host for example, could resume
  and send writes after another server had taken over.
- A restarting server could mistake a slow storage answer for silence, and take
  the lock from a server that was still renewing it.
- The server that lost the lock kept serving.

Schema apply, branch creation and deletion, and cleanup rely on one writer. In
0.15, every storage request checks the lease deadline before it is sent. A
restarting server takes the lock only when storage shows that the owner
stopped renewing. A server that loses the lock stops writing and exits with
code 2, so that your orchestrator can restart it. A 0.14 server that loses the
lock to a 0.15 server also stops at its next renewal. One gap remains: a server whose clock
stops, such as a suspended virtual machine, can still accept work for up to a
third of a lease. See
[restart after a failure](../user/operations/storage-failures.md#restart-after-a-failure).
#1221

When the answer to a conditional write on S3 or Azure is lost, Omnigraph now
sends the same request again and reads the object back, where it used to fail
the operation. #1176

## Other changes worth knowing

### Wrong results fixed

- A filter or mutation `where` that tested one nullable property twice, such as
  `not (s in ["x"]) or not (s in ["y"])`, also matched rows where the property
  was null. An `update` or `delete` with such a filter changed those rows too.
  Queries now return the right rows. If you ran an `update` or `delete` with
  such a filter, check the rows where that property is null. #1286
- `nearest()` now always ranks by L2 distance. Over a vector index that another
  tool built, it could rank by another distance or call approximate results
  exhaustive; it now ignores such an index and searches every row. Graphs whose
  indexes only Omnigraph built were not affected. #1299
- A branch created from another branch could lose access to its merge base
  once the parent branch was merged and deleted: diffs, `commit changes`,
  `query --snapshot` and the change feed answered `not_found`. They now read
  that commit while a live branch still depends on it. #1240

### Changes that used to be refused

- `schema apply` can make a nullable property required, and add `@unique` to a
  property of a node type that already has rows. It checks the stored rows
  first and changes nothing if a value is null or duplicated. Until now the
  only way was to export and rebuild the graph, which loses its commit
  history. #1271
- A `U64` query parameter above `i64::MAX` now binds. Send it as a decimal
  string, so that JSON clients keep every digit. #1102
- Whether a one-row `update` fit under `write_max_bytes` depended on which
  other rows shared its data file. It is now charged only for the rows it
  matches. #1304
- A keyed load of wide vectors was refused at about half of `write_max_bytes`.
  At the default limit, one load now fits about 2,630 rows of `Vector(3072)`
  instead of about 1,365. #1308
- An `update` that sets only plain properties on a type with Blob or vector
  properties now writes just those columns, where it used to rewrite whole
  rows with their Blobs. In a simulated test of 4 rows with 4 MiB Blobs, the
  update read 16.9 KB instead of 16.8 MB. #1272

### Indexes on branches

`omnigraph index build --branch <branch>` builds the indexes that a branch's
tables lack. Until now only `optimize` on `main` built them, so reads on a
branch scanned the data instead of using an index until the branch was merged.
The answers were correct, only slower. See
[build indexes](../user/operations/maintenance.md#build-indexes). #1150

### Running a server

- Memory: steady writes to one branch no longer keep up to 64 old versions of a
  busy table in memory. In a 1,500-commit test, the live heap fell from 203 MB
  to 136 MB. #1276
- Recovery: cluster and maintenance commands accept an `s3://` cluster root
  given on the command line, so you can unlock, optimize and clean up a stopped
  S3 cluster from the CLI. See
  [S3 cluster roots](../user/operations/s3-cluster-roots.md). #1189
- Tracing: the server can export OpenTelemetry traces when
  `OTEL_EXPORTER_OTLP_ENDPOINT` is set, and write JSON logs that carry trace
  IDs. Neither contains payloads or credentials. See
  [logs and traces](../user/operations/observability.md). #1001
- Cleanup: `cleanup` lists catalog versions instead of reading each one, so on
  a graph with a long history `cleanup --keep N` reads only the versions it
  keeps. It also no longer sends a request before each file it deletes.
  #1188, #1266
- Branches: `branch list --detailed` shows each branch's head, where it
  started, and when it was created and last moved, without reading each
  branch's history. #1012
- Audit: the server records which OAuth client acted for a person, in
  `GET /graphs/{id}/access` and in the policy decision log. #1196

### Managed clusters

- Human sign-ins now renew for 30 days instead of 8 hours, and a brief failure
  while renewing no longer forces a new login. #1199
- Unattended jobs can sign in with OAuth client credentials. See
  [workload profiles](../user/cli/managed-team.md#configure-an-unattended-workload-profile).
  #1154
- `cluster plan` and `cluster apply` wait until `--timeout` (300 seconds by
  default) instead of 10 seconds. If the time runs out, the result keeps the
  preview ID, so you can resume without submitting again. #1208, #1209
- `access`, `queries list` and `mcp` work with managed targets. #1179

### Agents, Studio and installation

- `query --format toon` prints results in TOON, which names each field once
  instead of on every row when the rows share their fields. Use it to put
  results into LLM prompts. #1198
- The agent skill that `omnigraph skill export` writes was corrected against
  the current CLI, and `omnigraph help` tells a new agent to read it first.
  #1215, #1198
- `omnigraph studio --target NAME` opens Omnigraph Studio on a configured
  server. #1137
- `nix build github:ModernRelay/omnigraph` builds the CLI and the server. See
  [Nix](../user/install.md#nix). #1153
- macOS binaries are signed with a Developer ID and notarized by Apple, so
  Keychain recognizes the CLI across upgrades. Moving from an older build may
  ask for one Keychain authorization. #1293

### Security advisories

Three dependencies changed because of security advisories:

- Arrow moves to 58.4.1 (RUSTSEC-2026-0442). #1270
- Tokio 1.53.3 or newer is required (RUSTSEC-2026-0386). #1145
- `crypto-bigint` 0.5 is removed (RUSTSEC-2026-0387). #1151

Omnigraph's own code does not call the affected Tokio API. The server used
`crypto-bigint` only to verify tokens, and it accepts the same tokens as
before. The updates clear these advisories from dependency scans.
