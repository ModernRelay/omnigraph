# RFC: Writer epoch fence on the branch manifest

> A term set in ***bold italics*** is being defined at that exact spot.

## Summary

Every graph branch gets a ***writer epoch***, a number on the branch's own `__manifest` naming the generation of the process allowed to move its head. A process ***holds*** an epoch for a branch only after a ***claim*** it published landed, a publication writing the next epoch onto the ***chain***, the branch's numbered `__manifest` versions; a reload never raises what a process holds, and a refusal clears it. Every publish through the publisher asserts the held epoch against the rows the publisher reloads on each attempt and is refused on a mismatch with the typed, non-retryable `WriterFenced`. After a takeover the older generation's publishes cannot land. On its bound branch, while it holds it, a process probes nowhere: its writes take the ***installed head***, the head the handle's coordinator keeps for its bound branch and the last publish there installed, as their authority, and its `Latest` reads bind the ***installed snapshot***, the snapshot of that head. The epoch is a ***control fact***, a `__manifest` row that changes no `table` row and no schema contract and records no graph commit; a claim moves no head and costs at most one version.

This is delta 7 of RFC 0013, "Monotonic `writer_epoch` in `__manifest`, CAS-claimed at writer init, checked on every publish", built as a control fact and claimed deliberately, never at writer init (Alternatives).

Unchanged: the next `__manifest` version written only if absent; `ExactGraphHead` on every ordinary write; the stamp route of [Graph access and cross-process writes](2026-10-16-graph-access-serving-and-cross-process-writes.md), whose control-fact stamp the row shares; the one-mutation-process boundary for schema apply, branch control and `cleanup`. Deciding that a writer is gone stays outside the engine.

## Motivation

Writer exclusion across processes is a sentence and two deployment-level locks: "Run one mutation-capable writer process per cluster" (`docs/user/deployment.md`), the cluster admission lock that servers and direct CLI writers acquire, and on Azure the Blob lease of `omnigraph-azure-admission` (`docs/dev/architecture.md`). No publish checks either. The deny list names the gap: "process-local locks presented as distributed writer fencing" (`docs/dev/invariants.md`). Every handle of one root shares one `WriteQueueManager` through `for_root` (`crates/omnigraph/src/db/write_queue.rs`); two processes share nothing.

The commit path is safe across processes: a publish lands only if the branch's head commit id and native branch identifier equal the ones its `WriteTxn` captured (`check_publish_precondition`, `crates/omnigraph-catalog/src/publisher.rs`) and the version is written only if absent. It cannot express ownership. Under one writer per branch, an agent's branch moved by the server that took the write and `main` by the cluster lease holder, a server that stalls, is replaced by a successor and wakes can publish with its head precondition intact, and the branch has two writers. A lock timeout does not close this: a paused holder wakes after any timeout and its late write carries no "now" the store can check.

RFC 0013 named the guard, delta 7: a monotonic `writer_epoch` in `__manifest`, a true cross-process conditional write, checked on every publish. Its step 5 bundled the epoch with the sidecar `PublishPlan`, delta 6; [RFC 0067](0067-detached-table-commits.md) removed the sidecar; the epoch was never built.

The same gap costs every operation a head read today, because no process can know the head is its own: one HEAD request before each warm read of the bound branch (`crates/omnigraph/tests/integration/warm_read_cost.rs`) and two probes per write, one at `open_write_txn` and one beside its staging in `early_revalidation` (`crates/omnigraph/src/db/omnigraph.rs`). A fence makes them redundant on a held bound branch; for `omnigraph-server`, whose handle is bound to `main`, that branch is `main`.

## User and operational behavior

Nothing changes until an operator raises a graph to the control-fact stamp (Compatibility) through the stamp-only route [Graph access and cross-process writes](2026-10-16-graph-access-serving-and-cross-process-writes.md) adds to `omnigraph upgrade`, which today refuses cluster addressing, and a process claims a branch. Before the stamp no row exists and no claim is accepted; after it every branch is at epoch 0, every process holds nothing, and every publish proceeds as today.

- **`branch claim <name>`** (CLI, direct or served; HTTP `POST /graphs/{graph_id}/branches/claim`, body `{"branch": "<name>"}`, a fourth `BranchAction`, `200 {"writer_epoch": N}`; in GQ a fifth branch statement on the grammar of [RFC 0055](0055-gq-branch-statements.md), dispatched like `branch create` at the `mutate` door and returning one row with one column `writer_epoch`, shipped once that grammar has landed) raises the branch's epoch by one, unless the calling process already holds it, and makes the calling process its ***owner***. The process that will write runs it: the successor for a handed-over branch, the admitted server for `main`, the server that created an agent branch right after `branch_create`, and after a server restart the orchestrator, through that server, for each agent branch it is to write; an orchestrator triggers it there, since nothing hands a held epoch over, and a claim by a process that exits leaves the branch with no owner and every writer refused until the next claim, so an operator claims through the server (`branch claim` on a server target), which then holds it. Every claim is explicit. One publish, no head move, accepted at any epoch; the current owner's claim returns its held epoch unchanged and publishes nothing. A lost acknowledgement is settled inside the operation (§The claim).
- **`--claim`**, a flag on every direct command that publishes, runs the same claim in the command's own process, on the branch the command publishes on and before its work; the command holds the branch until it exits. A `branch claim` by direct CLI ahead of the command does not serve it: that claim's holder ends with its process (§`main` and the lease), and the command, another process, holds nothing.
- **The refusal.** `WriterFenced { held, read, current }`: registry code `writer_fenced`, HTTP 409, `disposition.action` `refresh`, `disposition.effects` `none`, detail `writer_fenced: {held, read, current}`; `held` the process's epoch, absent when it holds nothing; `read` the epoch a claim read, present only when a claim is refused; `current` the rows' epoch; `is_retryable_publish_conflict` false. The staging is unreferenced and the collector reclaims it. The refusal clears the process's holder for the branch: it probes again from then on and its writes are refused until it claims. The caller reads `branch list --detailed` from the successor or by direct CLI, never from the fenced process, compares the epoch with the one it recorded, and claims only as a deliberate takeover. A client answered `writer_fenced` by a server holding nothing resends through the server the orchestrator routes the branch to; the detail names no server.
- **A process holding nothing on a claimed branch is refused**: a second server, direct CLI, maintenance beside the owner, a process that held a deleted branch of the same name (§The holder). A claim is writable graph work and runs under the cluster admission where one exists: on a cluster root the fence reaches a process admitted after the owner's lease was released or broken, on a standalone root every process. Maintenance on a claimed branch runs through the served route where one exists, today `optimize` of `main` ([Remote optimize through the serving owner](2026-10-29-remote-optimize-through-the-serving-owner.md), off until enabled); elsewhere the owner stops, the command runs with `--claim`, claiming the branch it publishes on (`main` for `optimize`, the named branch for `index build` and `repair`; `cleanup` publishes nothing through the publisher and claims nothing), and the server claims again. No branch is claimed until a claim runs, so out-of-band maintenance keeps working on every unclaimed branch.
- **A claim aborts a concurrent schema apply or settlement** on the branch with `ReadSetChanged`: both publish under `ExactGraphVersion`, refused on a version move, not retried, as `optimize`'s configuration commit already does to them.
- **`branch list --detailed`** (HTTP `GET /graphs/{graph_id}/branches?detailed=true`) gains `writer_epoch`: a required integer, `0` without a row or with only a row copied from the fork source, a row defined below as inherited; nothing else exposed; the human line prints it; no extra request; on a held bound branch it is served from the installed snapshot like every other read there.
- **Policy.** The claim takes its own action, `branch_claim`, target-branch scoped like `branch_merge`; a claim a request or `--claim` triggers is checked as `branch_claim` for that actor, a claim the server runs on its own behalf, after `branch_create` or after admission, is not policy-checked.
- **Operator responsibility.** The engine does not detect a gone writer and exposes the epoch, never the holder; an orchestrator records the epoch its successor claimed, decides by heartbeat, timeout or inspection, has the successor claim, and stops or restarts the fenced process, whose reads of its bound branch stay stale until its next publish is refused. The promise: once the claim's version exists, no publish by a process holding a lower epoch, or none, lands on that branch; of two claims racing for one branch, exactly one holds it.
- **The owner probes nowhere on its bound branch.** While a process holds its handle's bound branch, a write reads no head before or beside its staging and a `Latest` read reads no head before it runs; both use the snapshot of the owner's last publish, which a handle other than the one that published reloads once (§The owner's probes). The publish's load of the rows remains. A held branch that is not the handle's bound branch, and every branch a process holds nothing on, probes as today; for `omnigraph-server` that bound branch is `main` (Design). The window: after a takeover the older owner's reads are stale until its next publish is refused, which clears its holder; an owner that only reads is stale until the orchestrator stops or restarts it.

## Design

### The row

A control-fact row on the branch's own `__manifest`:

```text
object_id    = "writer_epoch"
object_type  = "writer_epoch"
metadata     = {"epoch": 3, "native": "agent-7.01JC…", "attempt_id": "01JD…"}
```

`epoch` is the generation; `native` the native branch the claim was published on; `attempt_id` the ULID the claiming operation minted before its first attempt, the control fact's identity as [Graph access and cross-process writes](2026-10-16-graph-access-serving-and-cross-process-writes.md) requires. The payload rides the `metadata` column as the `schema_contract` row's does; no record field is added. `ManifestRows` carries it as one optional field, the loader accepts the object type, `to_batch` emits it, and `ManifestState`, with the catalog `Snapshot` that copies its fields, carries the resolved epoch: the row's `epoch` when its `native` is the chain's, else 0. At most one row per branch.

A branch without a row is at epoch 0. A branch created from a source branch at version `v` carries the source's rows at `v`, this one included; a row whose `native` is not the chain's own is ***inherited*** and reads as 0. The new branch's first claim replaces it.

### The holder

A process holds, per root identity and branch name, the epoch of the last claim it landed, in a process-wide registry beside `for_root`'s (`crates/omnigraph/src/db/write_queue.rs`), not in the `WriteQueueManager`, which handles hold by `Arc` and the registry by `Weak`. Set only by a landed claim; never refreshed from a reload, reopen or read; cleared by a `WriterFenced` refusal; ends with the process. A process that has not claimed, or was refused, holds nothing.

The entry carries the native branch its claim was published on, as the row does. An entry whose native is not the chain's own is dropped by the publish or claim whose load finds it, and the process holds nothing there: a branch recreated under its name starts at epoch 0 on a new native branch, so what a process held on the deleted one never counts on it, equal epochs included.

The entry also carries the chain version of the process's last publication on the branch, through any handle, the claim included: each publication it lands raises it and nothing else does. The probe skip compares it (§The owner's probes).

### The check

The check runs in `publish_attempts`, on every attempt, over the rows `load_publish_state` loaded, before `check_publish_precondition`, for every precondition kind; `check_publish_precondition` gains one arm, the claim's kind (§The claim), the identifier compare alone, and is otherwise unchanged. No request. The rows' epoch is the resolved epoch above.

An ordinary publish asserts the holder, resolved against the chain's native (§The holder): nothing held and rows at 0, proceed at 0; holds `E` and rows at `E`, proceed; else `WriterFenced { held, current }`, not retryable, and the holder is cleared. A claim asserts what its first load read: `E` is the resolved epoch of the claim's first attempt; every retry asserts rows at `E` and writes `E + 1`; rows elsewhere, `WriterFenced` with `read` the `E` it read. A claim by the process that holds `E` with rows at `E` returns `E` and publishes nothing. The refusal precedes the put.

### The claim

`Omnigraph::claim_branch_writer`, reaching the catalog's `claim_writer_epoch`: a publication whose only change is the row, under a precondition of its own, `PublishPrecondition::ExactBranchIdentity { branch, branch_identifier }`, the name and identifier captured at the claim's first load; its arm in `check_publish_precondition` runs the identifier compare and returns before the head compare, so a branch recreated under the same name refuses the claim and a moved head does not. No other path writes the row. It is the first control-fact publication, a third kind beside a row publication with lineage and a no-op: no lineage intent, the loaded head unchanged, no `check_head_record` (the publisher's check that the loaded head matches the lineage row), no history settlement, `parent_commit_id` empty, `after_publish` with no new commit, the version put, and the lost-acknowledgement arm, which today returns in doubt for a publication without lineage, reading the attempted version's `writer_epoch` row instead. Today's publisher refuses a row change without lineage outside test builds; the rule becomes the graph-access RFC's, a publication that changes `table` rows or the schema contract records a graph commit, one that writes only control facts records none. That RFC owns the rule; this RFC implements it first; the graph-access RFC's registration, tombstone and drop record publish through the same kind (Rollout, phase 4).

A lost acknowledgement is settled by the graph-access RFC's read-back: the attempted version holding a `writer_epoch` row with this attempt id is the claim landed; another's attempt id with no acknowledgement, lost; after an acknowledgement, or when the read-back fails, in doubt. Lost answers `writer_fenced` with `read` the epoch read; in doubt answers `outcome_unknown`, `disposition.action` `reconcile`, and the caller reads `branch list --detailed` before claiming again. The head read-back cannot tell two claims apart, which is why the attempt id is on the row.

Two claims racing read `E` at chain version `N` and target `N + 1`: one lands with `E + 1`; the other's retry finds `E + 1`, not `E`, and is refused.

### The race with a late write

The successor's claim and a write by the owner holding `E` both target `N + 1`. The older write lands first: a legitimate last write of its generation; the claim's retry reloads, the rows are still at `E`, its precondition reads no head, it lands at `N + 2`; the older generation's next publish asserts `E` against `E + 1` and is refused. The claim lands first: the older write's retry asserts `E` against `E + 1` and is refused, its staging unreferenced. The version number orders both, which is why the epoch lives on the chain the publisher compares and swaps on.

### The collector

`StagingWitness` records `omnigraph.staged_against_branch_incarnation` and `omnigraph.staged_against_graph_head` (`crates/omnigraph-core/src/staging.rs`); this RFC adds `omnigraph.staged_under_writer_epoch`, the staging process's held epoch or 0. `judge_staging` gains one Dead case before the head comparison: a recorded epoch below the branch's resolved epoch in the run's snapshot. `BranchView` gains the epoch from the `Snapshot` the collector opens per live branch, which carries it from `ManifestState` (§The row); a staging without the property is judged by head alone; no age enters.

### The owner's probes

The probes are head reads the fence makes redundant: on a held branch no other process can move the head. Today a write probes the head at `open_write_txn`, again beside its staging puts in `early_revalidation`, and revalidates under its gates in `revalidate_write_txn_with` (`crates/omnigraph/src/db/omnigraph.rs`); a `Latest` read on the bound branch probes in `resolve_target_inner` through `probe_latest_incarnation`. The installed head exists for the handle's bound branch only. While the process holds that branch all four sites skip: the write takes the installed head as its authority, the object `write_authority_for_known_branch` builds today, no probe runs beside staging, revalidation compares against the installed head alone, the read binds the installed snapshot. The installed head is a handle's own: each `Omnigraph` open builds its coordinator, a publish installs on the handle that ran it (`install_coordinator`), and a view from `with_runtime_bindings` shares its parent's. A second handle of the owner process would otherwise never see the first one's publishes, so a handle skips only while its installed head is not behind the version the holder records (§The holder), a comparison in memory; behind it, the handle reloads its head, as it does today when a probe finds the head moved, with no head read before, and then skips. A held branch that is not the bound branch probes as today; `omnigraph-server` opens its handle bound to `main`, so its skip reaches `main` and the agent branches it holds keep their probes. The publish's load in `publish_attempts` remains and asserts the epoch.

A wrong assumption costs a write nothing new: on a held branch a claim is the only publication of another process that lands, so the owner's publish after it is refused at its load with `WriterFenced`, the holder is cleared, and the write is refused; nothing redoes it. `optimize`'s configuration commit, outside the publisher (§Publications outside `publish_prepared`), moves the version and neither a row nor the head: a read binds the same rows and a write lands past it, as today. It costs a read staleness: rows from before the successor's publish until the owner's next publish is refused and clears the holder, or until the orchestrator stops the owner. On an unclaimed branch nothing is held and nobody skips. Two developer-guide passages change: the bound-branch revalidation sentence of `docs/dev/writes.md` and the read-view freshness paragraph of `docs/dev/architecture.md` each gain the clause that the installed head is the complete authority while the process holds the branch's epoch.

### `main` and the lease

`main` is a branch. The cluster admission lease the server acquires in `acquire_server_graph_admission` (`crates/omnigraph-server/src/lib.rs`, through `omnigraph-cluster`) is the decider: that server claims `main` after admission and before it serves (rollout phase 3). Admission is absent for a standalone root, whose `main` an operator claims through the server (`branch claim` on a server target), which then holds it, or nobody; a direct claim holds only until the CLI exits. The Azure wrapper `omnigraph-azure-admission` is a supervisor that starts the server and publishes nothing. Under a cluster, a process never admitted holds nothing for `main`. The lease module's own "claim" names its superseded-marker file and is unrelated.

### Publications outside `publish_prepared`

Every publication through the publisher asserts its process's holder, the ones with no ordinary write transaction included: `repair`'s pin-adopting publish, schema apply's and settlement's `ExactGraphVersion` publications, the system-column upgrade, and the publication of an unpublished commit, a proposal written with `as commit`, which asserts the publisher's holder and not the proposal's captured authority. Two writers of the branch sit outside the publisher and assert nothing: `optimize`'s configuration commit, a Lance `update_config` commit (Invariants, not fenced), and `omnigraph upgrade`'s stamp-only route, which writes no row and runs with every writer stopped.

- **`:744-746` and `:748-752`**, "`check_publish_precondition` fails closed, whatever the precondition, when a fact names the attempt's branch, name or candidate" and the refusal table: gain a fourth row, the writer epoch on the branch's own chain, refusing when the rows' epoch is not the one the attempt holds, `writer_fenced`; and the sentence "the writer epoch is checked in `publish_attempts` before the precondition, the other facts in `check_publish_precondition`".
- **`:898-899`**, "a fact that does not name them never makes them refuse": becomes "a fact that does not name them never makes them refuse; the writer epoch names no attempt and refuses a whole generation by comparison".
- **`:884-889`**, "that route's one publication on main registers every live branch" and "each other branch takes the stamp with its next publication": become "that route raises every live branch, as today's does, and its publication on main registers them".

## Invariants

Against [the architectural invariants](../dev/invariants.md):

- **3, one coherent accepted view.** The epoch is the process's holder, set by a claim, asserted at the publish's load, never revalidated from a reload; an ordinary publish's retry asserts the same holder, a claim's the value its first load read. On a held bound branch the fence makes the installed head the complete authority, so the revalidation reads nothing and the write's view is still one view captured once. Freshness: today a bound-branch capture reflects every publish completed before its probe, from any process; on a held branch it reflects every publish the owner process completed, through any of its handles, and after a takeover may omit the successor's until the older owner's next publish is refused or the orchestrator stops it, a stated bound. A process holding nothing keeps the probe.
- **5, crash convergence.** One more proof that a staging's authority is gone, the branch's epoch above the recorded one; age proves nothing; no side record.
- **8, integrity failures are loud.** `WriterFenced` is typed.
- **11, bounded failures.** `WriterFenced` is not retried; the claim's read-back is bounded by the publisher's attempt budget.
- **12, one source of truth.** The row is the only record of the branch's epoch; the process's holder is a copy of what it published, never commit authority. The lease says who may claim `main`, the row says that a claim landed. The row carries no fact the chain already holds.
- **13, evidence matches the boundary.** Compatibility, refusal, crash and rebuild evidence on checked-in instruments, below.

Deny list: "process-local locks presented as distributed writer fencing" is what this RFC stops relying on; the gates stay contention optimizations. "Silent retries" and "acknowledgement before durable graph visibility" are untouched: a claim is acknowledged when its version exists, a refusal is never retried.

Support boundary, "Branch creation/deletion and cleanup retain their existing single-writer-process control boundary": unchanged. The epoch fences publications through the publisher only. Not fenced today: Lance ref metadata puts (`replace_metadata`), ref unlinks and deletes, the collector's deletes of refs and trees, `optimize`'s configuration commit. The ref and collector writes become fenced once their first durable step is a publication, which the graph-access RFC's control facts make of them; `optimize`'s configuration commit waits for a change of its own; the sentence stays until then.

No invariant is weakened.

## Compatibility and reversibility

- **Storage.** An older loader refuses the row with "object type … this storage format does not hold" (`crates/omnigraph-catalog/src/state.rs`), so the row lives under the control-fact stamp of [Graph access and cross-process writes](2026-10-16-graph-access-serving-and-cross-process-writes.md) and its route: only the stamp-only route that RFC adds to `omnigraph upgrade` (which today refuses cluster addressing) raises a graph, every live branch, writers stopped. Until then the new binary writes no row and accepts no claim. A branch at the new stamp is refused by an older binary at open through `guard_stamp` (`crates/omnigraph-catalog/src/migrations.rs`; today `INTERNAL_MANIFEST_SCHEMA_VERSION` 16, floor 14). The stamp is per `__manifest` branch. [Schema apply with live branches](https://github.com/ModernRelay/omnigraph/pull/963) also proposes a stamp; whichever lands second takes the next one.
- **Two lines that whichever RFC first raises the stamp changes** (`crates/omnigraph-catalog/src/commit.rs`). Today every publish writes the binary's constant as the stamp; under the route rule a publish writes back the stamp it loaded and only the route raises. And `overwrite_probed` carries a version's cold block-registry fragments only when the branch's stamp equals the constant (the `read_stamp` comparison); the 15 to 16 raise of [PR 956](https://github.com/ModernRelay/omnigraph/pull/956) crossed it. The predicate becomes "at or above the stamp cold fragments arrived with", or the route carries them, with a test: a stamp-16 branch holding cold fragments is raised and keeps its registry.
- **Mixed binaries.** Before the upgrade, as today. After it, an old binary's open or publish on any live branch fails the stamp guard with HTTP 400 `bad_request`, "is stamped at internal schema v17 but this binary reads only v14 to v16", with the stamp the order with PR 963 assigns in place of v17, today's rule for every raise.
- **Wire.** One conflict kind and registry code, one command, one flag on the direct commands that publish, one HTTP route, one GQ statement on the branch-statement grammar of [RFC 0055](0055-gq-branch-statements.md) once that grammar lands, one `branch list --detailed` field, one policy action. No existing field changes. No Lance behavior changes.
- **Downgrade.** Export and load.
- **Revert.** A release whose loader keeps the row kind and whose stamp-only route raises every live branch once more, dropping the row, with writers stopped; the reverted binary starts after the route; the check, the claim and the probe skip are removed.

| Alternative | Reason not selected |
|---|---|
| No epoch: the cluster admission lock, the Azure lease and the one-process rule, as today | The minus-one design. Fails at the takeover: a stalled lock holder wakes after a successor started, its head precondition holds, its publish lands, two writers share a branch. Outside today's support boundary, which the one-writer-per-branch direction requires lifting |

The chain is what every publish reads |
| The epoch in the Lance ref's `BranchContents` metadata | `replace_metadata` is "one-object publication, without a native CAS" (`crates/omnigraph-core/src/branch_control.rs`): two claims both land |
| A lease with a timeout, in the engine | A paused holder wakes after any timeout; a late write carries no "now". The lease decides who may claim; it cannot fence |

The holder's version is one comparison in memory |
| Maintenance on a claimed branch through served routes only | `schema apply`, `index build`, `index rebuild` and `repair` are direct commands with no served route, so every claimed branch would lose them until one exists. `--claim` keeps the direct commands and keeps the claim explicit |

Precedent audit. Origin: RFC 0013 delta 7, a `writer_epoch` field of its `PinnedSnapshot` and `Expectations`, never built; here a control-fact row, claimed deliberately. RFC 0013 exempted maintenance commits from the epoch; this RFC fences every publication through the publisher and leaves what sits outside the publisher unfenced (Invariants). Nearest landed pattern: `StagingWitness`, the authority a publish compares on recorded in the staged transaction; the epoch property extends it. The `schema_contract` row: a non-table row with its payload in `metadata`. The stable-identity `Allocator` (`crates/omnigraph-compiler/src/catalog/schema_ir.rs`) rests on the contract's `ExactGraphVersion` publication and the main-only schema rule, not on a single-writer rule. SlateDB keeps `writer_epoch` inside its own manifest, the object it compare-and-swaps, and fails the old writer's next operation with `Fenced` (`slatedb/src/manifest/store.rs`, `slatedb-txn-obj/src/lib.rs`); it diverges in four places: a bump at every writer open, a check on every manifest refresh, a separate `compactor_epoch` for maintenance, a fence entry in the next WAL slot after the bump; here the claim is deliberate, the fenced writer learns at its next publish, maintenance asserts the same holder, the version CAS is the one layer.

## Rollout

1. **The row, the holder, the check, the claim API, the control-fact publication kind**, under the control-fact stamp with its upgrade route and the two `commit.rs` lines unless already landed. Nothing changes before a graph is upgraded; after it, epoch 0 everywhere, no claim until phase 2's command.
2. **The collector by epoch, `branch claim` in CLI and HTTP (the GQ statement once RFC 0055's grammar has landed), `--claim` on the direct commands that publish, the `branch_claim` action, the `branch list` field, the owner's probe skip, and the server claiming each agent branch it creates.** From here a branch a server creates is held by that server; after a restart the orchestrator claims, through the server, each agent branch it is to write.
3. **`main` claimed after admission** by the cluster lease holder, whose `main` reads then run probe-free. Precondition: `main`'s maintenance through the served route and schema apply through a served route no RFC adds today ([Graph access and cross-process writes](2026-10-16-graph-access-serving-and-cross-process-writes.md) keeps `schema apply` direct), or both by the stop, run with `--claim`, claim-again procedure (User behavior).
4. **Consumers.** The graph-access RFC's registration, tombstone and drop record publish through the control-fact kind under the same assertion; the merger's takeover of abandoned branches follows in its own change.

`implementation` moves to `in-progress` at phase 1 and to `complete` at phase 3.

Implementation note, 2026-11-13: phase 1 and, from phase 2, the `branch_claim` action and the owner's probe skip shipped in 0.16.0 (#1350). No command or route claims a branch yet, so only a program embedding the engine can claim one, and once it does, `omnigraph-server` and the CLI are refused there with `writer_fenced` until another claim.

## Unresolved questions

- **Who may claim a held agent branch.** Phase 3 binds the claim of `main` to the cluster lease, and the creating server's claim right after `branch_create` is decided (phase 2). For the takeover of a held agent branch, whether any admitted server may claim or only the control plane may trigger it is decided by the maintainers of this RFC and of [Graph access and cross-process writes](2026-10-16-graph-access-serving-and-cross-process-writes.md) together, before phase 2 ships the command. This RFC requires only that every claim be explicit, never a retry's side effect.

## Decision log

- 2026-11-09: Created. The decisions, each with what it rejects:
  - **Where the epoch lives.** A control-fact row on the branch's own `__manifest`, one per branch, under the control-fact stamp and its upgrade route: the chain is what every publish reads and compares on. Rejected: its own object, a second read and a second order per publish; the Lance ref's metadata, which has no native CAS; one epoch per store, which fences every other branch's writer.
  - **Who holds it.** A process, only after an explicit claim it published landed. Rejected: a claim at every writer init, where every open fences the previous opener; an implicit claim by a branch's creator, a two-valued holder state and a policy hole for one saved publish; adopting the rows' epoch on a first publish, since a restarted old owner is a new process and would rejoin a branch a successor holds.
  - **The holder.** In a process registry, not in the `WriteQueueManager`, which ends with the root's last handle. A `WriterFenced` refusal clears it, since a fenced owner would otherwise skip its probes and read stale for the life of its process. The owner's own claim returns its epoch and publishes nothing, so a caller that lost the answer can ask again.
  - **The claim.** A publication under its own precondition, `ExactBranchIdentity`, since no existing precondition compares the branch identifier without the head; settled by the attempt id on the row, since a head read-back cannot tell two claims apart. The row carries the native branch it was claimed on and an inherited row reads as 0, so a fork starts unclaimed.
  - **What is fenced.** Every publication through the publisher, a publication of an unpublished commit asserting the publisher's holder and not the proposal's captured authority. `optimize`'s configuration commit stays unfenced, a Lance commit outside the publisher. The collector judges staging by epoch before head.
  - **The refusal.** `WriterFenced` is not retried; its disposition is `refresh`, the state and not the request having refused; a refused claim reports the epoch it read in a field of its own.
  - **The owner's probes.** Skipped on the handle's bound branch while the process holds it, the only branch with an installed head, which for `omnigraph-server` is `main`: on a held branch only a claim moves the chain. A fenced owner that only reads stays stale until the orchestrator stops or restarts it; the engine refreshes nothing on its own, since deciding that a writer is gone stays outside it.
  - **Gates.** The GQ spelling of the claim waits for RFC 0055's grammar, since product behavior takes no authority from a draft. The tombstone's relation to the epoch is decided with the graph-access RFC (`blocked_on`); this RFC prefers a tombstone row of the same family, so a tombstoned branch keeps its last epoch.
- 2026-11-09, from review of the RFC PR. Three decisions, each with what it rejects:
  - **The holder's branch.** The entry carries the native branch of its claim and counts only on that chain: the epoch restarts on a branch recreated under its name, so the number alone let a process that held the deleted branch at `E` publish on the new one at `E`. Rejected: carrying the epoch across a delete, which waits on the tombstone decision (`blocked_on`).
  - **The probe skip with several handles.** A handle skips only while its installed head is not behind the version the holder records for the process's last publication, and reloads when behind: the installed head is a handle's own, so a second handle of the owner would otherwise read its old snapshot with nothing to end it. Rejected: one installed head shared by a process's handles, a change larger than the fence; the skip for a single handle only.
  - **A claim for a direct command.** `--claim` runs the claim in the command's own process: a `branch claim` by direct CLI ends with its process before the command starts, so the stop, claim, run procedure had no surface to run on. Rejected: served routes only, which no RFC adds today for `schema apply`, `index build`, `index rebuild` or `repair`.
