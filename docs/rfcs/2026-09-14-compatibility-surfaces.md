# RFC: Compatibility surfaces

> A term set in ***bold italics*** is being defined at that exact spot; it is plain text everywhere after.

## Summary

OmniGraph has seven shapes that something outside the process depends on: the HTTP wire, the CLI's `--json` output, the GQ language, the PG language, `cluster.yaml`, the policy contract (the Cedar schema and the policy file operators write), and the storage format. This RFC calls each of them a ***compatibility surface***, a shape whose change can break a consumer that was built against the old one, and gives the first six the version the storage format already has, set by hand, plus a checked-in record of the surface's current shape and a test that fails when the code no longer matches the record, which today only the HTTP wire has, as its whole-document golden.

The record is a ***hash file***, one per surface, holding one SHA-256 per ***unit***, the smallest piece of the surface a change is reported at (one HTTP schema, one CLI command's output, one grammar rule, one config type, one Cedar action). A regenerated hash file's diff therefore names what moved. The version is a `(major, minor)` pair: major when a consumer built against the old surface can break, minor otherwise. Compatibility is directional: what a surface produces must stay readable by an old reader, so removing a field, narrowing a type, or adding a value to a closed output enum is major; what a surface accepts may widen, so a new optional request field, `cluster.yaml` key, or grammar alternative is minor. Each surface also has a ***root hash***, one SHA-256 over its unit map, the surface's identity in one string. One response record lists every surface's version and root hash so a release note, a client, or a teammate can say "the HTTP wire is at 1.2" instead of reading a diff, and a client can tell two builds apart even at the same declared version.

This RFC is the parent of the per-surface rules: it names the surfaces, fixes the one mechanism, and lists every version in one record. A surface whose number already has its own RFC keeps that RFC as the authority, and this one only lists it. The storage format is that case: the "One storage format version" draft, not yet in the registry, folds the storage-side numbers into one stamp, and this RFC reports the stamp.

What does not change: the existing domain payloads of every surface, the storage layout, and the byte-exact `openapi.json` golden, which stays the exact HTTP specification beside the hash file. The HTTP wire gains only the additive field, route, header, and error code this RFC names.

## Motivation

The question "did the API change, and is the change breaking" has no answer today for five of the seven surfaces, half an answer for the HTTP wire, and a version-only answer for the storage format.

- The HTTP wire is gated: `openapi.json` at the repository root is compared byte for byte with the served document by `openapi_spec_is_up_to_date` in `crates/omnigraph-server/tests/openapi.rs`, regenerated with `OMNIGRAPH_UPDATE_OPENAPI=1`, and CI fails on drift. The document's `info.version` is the crate version, so it says which build produced the spec, not whether the wire is compatible with the previous one. No header or field on any response tells a client which wire it is talking to.
- The CLI's `--json` output mostly goes through one function, `print_json` in `crates/omnigraph-cli/src/output.rs`; the change-feed commands write one incrementally stitched document through their own writers in the same file, four maintenance commands (optimize, repair, cleanup, rebuild) build `serde_json::Value` envelopes in `main.rs`, the managed control-plane commands build theirs with `json!`, and `read --format jsonl` has its own line writer. Most payloads are the shared `omnigraph-api-types` structs, but eleven output types are private to the CLI and two call sites build inline `json!` values. Tests probe individual fields through `serde_json::Value`; the parity matrix pins the local arm equal to the remote arm; nothing pins one release's shape against the next. Scripts and operator tooling consume this surface.
- The GQ and PG grammars (`crates/omnigraph-compiler/src/query/query.pest`, 86 rules; `src/schema/schema.pest`, 39 rules) are the durable contract of every stored `.gq` and `.pg` file: stored queries persist as text and are re-parsed at boot. The parser tests and the 83 GQ logic cases (RFC 0045) pin behavior, none pins the grammar's shape, and no version names the language.
- `cluster.yaml` deserializes into `RawClusterConfig` and its nested types, most of them `deny_unknown_fields` structs (the untagged `QueriesDecl` enum in `config.rs` is the exception), so a renamed field fails loudly, and a `version` field pinned to 1. No test pins the accepted key set, so an added optional field or a removed serde alias (`EmbeddingProviderConfig.kind` accepts `provider`) is invisible to the suite.
- The policy contract has two halves and no version on either. The Cedar schema is a Rust string literal, `policy_schema_source()` in `crates/omnigraph-policy/src/lib.rs`, four entity types and ten actions; no test enumerates them, so an added action is invisible to the suite. The policy file operators write deserializes into the policy crate's own `PolicyConfig` and `PolicyAllowRule`, which carry a `version: 1` and fields such as `target_branch_scope`; renaming one breaks every deployed policy file while nothing in the repository names the change.
- The storage format is versioned (`INTERNAL_MANIFEST_SCHEMA_VERSION`, currently 9) with refusal and upgrade rules of its own (RFC 0064), and the "One storage format version" draft folds the remaining storage-side numbers into that one stamp. It is the model the other six catch up to, and this RFC only lists its version beside theirs.

Polars solved the same problem for its one surface, the serialized `DslPlan`: every DSL type renders a JSON schema, a checked-in `dsl-schema-hashes.json` stores one SHA-256 per type, a build script folds that file into one root hash embedded in the binary, a CI job regenerates the hashes and fails on drift, and a serialized plan carries the root hash so a structurally different build refuses it. Its `DSL_VERSION` comment records the division of labor exactly: the hashes check compatibility, and the version moves only for "a breaking change that doesn't change the schema hashes" (`crates/polars-plan/src/dsl/plan.rs`, Polars `e7868fec77`). Polars' schema-hash refusal is the default and carries an explicit bypass; its version bump for a semantic change with unchanged hashes is the case this RFC keeps as well. OmniGraph has seven surfaces where Polars has one, so the mechanism is applied per surface, each with its own owner, file, and version.

An issue or a local fix is not enough because the gap is the absence of a rule, not a bug: nothing today obliges an author to say which surface a change touched. The maintenance cost is one test, one file, and one constant per surface, in the idiom three existing tests already use.

## User and operational behavior

**Authors.** A change to any surface fails the surface's check test with the list of added, removed, and changed units and the regeneration command. The author first bumps the surface's version constant by the directional rule in the Summary (a produced shape an old reader can no longer consume is major, so is any removed unit, everything else minor), then runs

```
OMNIGRAPH_UPDATE_COMPAT=1 cargo test --workspace --exclude omnigraph-gqt
```

which writes the current constant into the hash file, then runs the same tests without the variable and commits the file with the change. The order matters: regenerating first writes the old constant into the file, and the bump afterwards recreates the drift. A reviewer reads the hash file's diff as the list of units the PR touched and the units file's diff as the change inside each. A breaking change the renderer cannot see (a typechecker bound tightened that no case's expectation covers, a stored `.gq` that stops being accepted) is a major bump with an unchanged unit map, allowed, and the reviewer demands the regression case (a `.gqt` case or a test) in the same PR. `AGENTS.md` gains this route, in this order, beside the existing `openapi.json` one.

**Operators and clients.** `GET /healthz` returns, in addition to today's fields, a `compat` record naming every enrolled surface's version and root hash beside the storage format's version. `GET /compat`, unauthenticated like `/openapi.json` (it names nothing the public repository does not) and flat like `/healthz`, returns the same record together with each enrolled surface's unit map, so a client or an operator can see which units a server's build has without the repository. Every HTTP response carries one header, `omnigraph-http-api: <major>.<minor> root=<sha256 hex>`, and the CLI sends the same header, with its own values, on every request. `omnigraph version --json` prints the same record from the CLI's own build, the CLI JSON surface included, which the server cannot report since it does not depend on the CLI crate.

Refusal happens before effects, at the server. The CLI in remote mode sends its own `HTTP_API_VERSION` and the HTTP wire's root on every request in the `omnigraph-http-api` header; the server reads the version at admission, before authorization and before any write, and a different major, or a header that does not parse as `<u16>.<u16> root=<64 hex>`, is refused with the typed error `api_version_mismatch` naming both values, so a `DELETE` on a branch is never applied and then reported incompatible. A request with no header is admitted as a pre-RFC client. The unauthenticated routes (`/healthz`, `/readyz`, `/openapi.json`, `/compat`) never refuse: a client must be able to learn the server's version before it can match it. When a response header carries a different major, which a proxy that dropped the request header or a mixed fleet can produce, the CLI discards the body and reports a distinct outcome, `api_version_incompatible_response`, that keeps the HTTP status and states that whether the request took effect is not established by this check: a response header cannot prove that a write did not happen, and only the server's admission refusal carries that guarantee. On those same routes the CLI does not refuse: it reports the different major as a warning and keeps the body, since they are how it learns the server's version. Refused rather than warned because a major means a field the client relies on may be gone, and a warning that lets a wrong read through is the case nothing repairs afterwards. A server older than this RFC ignores the header on the request; against such a server the CLI's only signal is the absent header on the response, and it warns and continues, since it cannot know whether a refusal would come before or after the effect.

The CLI also checks every response, at one seam in its HTTP client that every remote path passes (JSON, streamed change feeds, blob and export bodies), before any byte of the response is decoded or printed: a server minor lower than the client's is a warning, a higher server minor is silent; an absent header is the pre-RFC warning above; a header that does not parse as `<u16>.<u16> root=<64 hex>` is treated as absent and the warning names the value; when the versions agree but the roots differ the CLI warns once, "same declared version, different structural identity", which is what it can truthfully say (two branches may each have bumped to the same version). Warnings go to stderr and never into `--json` stdout. The CLI never calls `/compat` for these checks; the one header carries everything they read. Local (embedded) mode never checks: there is no second process.

**Releases.** Every release note under `docs/releases/` for a release after the one that ships phase 4 carries a block headed `## Compatibility surfaces`, one line per surface in the form `<surface name> <version> (was <previous>) added: <keys> changed: <keys> removed: <keys>`, the `was` clause present when the version moved, an `added:`, `changed:`, or `removed:` clause present only when it has keys, a surface whose version and unit map did not move printing `<surface name> <version>` alone, the surface named as the record spells it (`http_api`), the keys being those that moved since the previous release tag. The block is generated, never typed: `scripts/compat-release-block.py <previous tag> [<release ref>]` reads the hash files at the two refs (the release side defaults to the working tree) and prints the block; `scripts/check-docs.py` runs the same generator for each note under `docs/releases/`, with the previous tag taken as the highest release tag below the note's version and the release side taken as the note's own tag when it exists and the working tree before the tag is cut, and fails the documentation check when the note's block differs or is absent. The documentation job (`check_agents_md` in `ci.yml`, which runs `scripts/check-docs.py`) fetches tags for this rule; its checkout carries none today. Earlier notes are exempt by version, so the rule is green on the tree the day it lands. A release note cannot merge with the block missing; the tag itself is not gated. The block is what a script author reads first; the diffs behind it are in the units files at the two tags.

**One change, end to end.** A developer removes the field `internal_schema_version` from `HealthOutput`. `cargo test` fails in the HTTP check test, `changed: schema:HealthOutput`, with the regeneration command, and in `openapi_spec_is_up_to_date`. An old reader can no longer consume the shape, so the developer bumps `HTTP_API_VERSION` from `(1, 0)` to `(2, 0)`, regenerates `openapi.json`, the hash file, and the units file, and runs the tests again, green. The pull request now shows the code change, the constant, the `openapi.json` diff, three moved entries in the hash file (the major inside `version`, `root`, `schema:HealthOutput`), and the field's removal in the units file. The floor sees a moved unit map with a larger version and passes; the semantic diff reports a removed property and agrees with the major; the cross-version job's every command is refused at admission with `api_version_mismatch`, and the job passes with the report that the head's major differs from the previous release's, since it measures compatibility only within a major. Had the developer bumped minor instead, and had the field lived in a shape the list decodes, `CommitListOutput` under `commit list --json`, the old CLI's deserializer would have errored on the missing required key and the job would have failed. After the release, every response says `omnigraph-http-api: 2.0 root=…`, an old CLI sending `1.0` is refused at admission with `api_version_mismatch`, and the release note's compatibility block reads `http_api 2.0 (was 1.0) changed: schema:HealthOutput`.

**Executed compatibility.** Shapes are checked by hashes and classified by people; the wire itself is checked by running the old consumer. CI already installs two pinned release binaries for the storage upgrade suites (`scripts/install.sh` with a `VERSION` pin); a job installs the previous release's CLI the same way, with the pin moved at every release, and drives it against a server built from the pull request, started with `--unauthenticated` and loaded from a checked-in fixture (schema, rows, one stored query) by the head's own CLI, through a fixed command list (graph listing, reads, a stored query, `--json` output of each). It fails when any command errors, except when the head's `HTTP_API_VERSION.0` differs from the previous release's, when every command is refused at admission and the job passes, reporting the major; an error is how a missing required field shows, since the old CLI's deserializer refuses it; a missing optional field is invisible to this job. A failure means an old reader broke, and the PR carries a major bump or restores the shape. This is the one check in the design that measures compatibility instead of declaring it.

**Deprecate before remove.** A unit may be removed only after a release in which it was marked deprecated: `deprecated: true` in the OpenAPI document for HTTP units and on the type for every `ToSchema`-rendered unit (CLI, `cluster.yaml`, policy file), a `@deprecated` annotation for a Cedar unit, all inside the hash since the stripping rule removes only `description`, `summary`, and `example`; a unit whose rendering has no place for a marker (a grammar rule, a reference unit, an HTTP security scheme, whose utoipa type carries no `deprecated` field) is deprecated through its surface's checked-in list, `crates/<crate>/compat/<surface>.deprecated.txt`, of that surface's unit keys, which the floor reads in place of the marker; the lists are per surface, so a deprecated `rule:ident` in GQ never licenses the removal of PG's `rule:ident`. The baseline for the marker is the newest release tag that is an ancestor of the head (`git describe --tags --match 'v*' --abbrev=0`; the `test` job fetches the release tags, as Evidence and tests states), never a comparison of version numbers, so a head whose package version still equals the last release finds that release; every removal therefore takes two releases, one to warn and one to remove; a removed key absent at that tag never shipped and needs no marker.

**The rule applied to people, and its seats.** Two rules land on every author: regenerate the hash file when its check fails, and bump the version when the hash file changes. The tables below record the ways to satisfy each rule without doing the work, and the honest routes the documentation gives an author.

| Evasion (satisfy the rule without doing the work) | What stops it |
|---|---|
| Regenerate blind and never read what moved | the hash file's diff in the PR lists the moved units by name; the advisory `.github/CODEOWNERS` requests the crate owner's review on every `compat/` diff; nothing blocks the merge, so the reviewer's read is the stop, and a sorted list of moved units keeps that read short |
| Bump minor on a removal | the CI floor (Rollout phase 4) refuses any bump but a strictly larger major when a unit key present on the base is absent on the head; a removal inside a unit only moves that unit's hash and stays the reviewer's call |

|---|---|
| Change the API, run `OMNIGRAPH_UPDATE_OPENAPI=1 cargo test -p omnigraph-server --test openapi`, commit (`AGENTS.md` today names the variable; the test's failure message carries the command) | yes, once the same paragraph reads: bump the surface version, then regenerate `openapi.json` and the hash file (`info.version` carries the bump, so the golden moves too), then the plain tests |

## Design

### Definitions

- **Compatibility surface**: a shape a consumer outside the process depends on. Seven exist; this RFC instruments six and lists the seventh.
- **Unit**: the granularity a change is reported at within a surface. Units are named, and the name is the key in the hash file.
- **Canonical bytes**: the one encoding every hash is computed over: JSON with object keys sorted recursively, array order kept, no whitespace, UTF-8 with serde_json's default escaping (control characters, quotes, and backslashes only), numbers as serde_json renders them, no trailing newline. A fixed input and its expected hash are checked in as a vector so the encoding cannot drift.
- **Hash file**: `crates/<crate>/compat/<surface>.hashes.json`, checked in, `{"version": [major, minor], "root": "<sha256 hex>", "units": {"<name>": "<sha256 hex>" | {"ref": "<surface>/<unit key>", "hash": "<sha256 hex>"}, ...}}`, pretty-printed with keys sorted and a trailing newline, so its diff is a list of moved units. Hex is lowercase. A unit whose root shape belongs to another surface is recorded as the reference form, not hashed a second time as a root (a shared type nested under a private root stays inside that unit's `$ref` closure); the root covers references by their text, target hash included, so a change behind a reference moves this surface's root too; the renderer refuses a reference whose target key is absent from the referenced surface's hash file or whose recorded hash differs from the target's.
- **Units file**: `crates/<crate>/compat/<surface>.units.json`, checked in beside the hash file and regenerated with it, holding, under the same keys, the rendering each unit's hash is computed over, pretty-printed; a reference unit holds the same `{"ref": ...}` object. It is what a reviewer diffs: the change itself, not a moved hash. The check test compares it too. The `openapi.json` golden stays as the exact document; the HTTP units file is its per-unit view.
- **Surface version**: `pub const <SURFACE>_VERSION: (u16, u16)` in the crate that owns the surface's constant. Every surface starts at `(1, 0)`.
- **Check test**: one `#[test]` in the crate that owns the surface's renderer, which renders every unit to canonical bytes, hashes it, recomputes the root, and compares units, root, and version with the hash file and every rendering with the units file.
- **Root hash**: SHA-256 over the canonical bytes of the unit map alone (the version is not covered); the surface's identity in one string, the counterpart of Polars' `DSL_SCHEMA_HASH`. Stored in the hash file as `"root"`, embedded in the binary through `include_str!` of the hash file, and served. How the embedded root follows a regeneration is developer documentation, arriving with phase 1.

### The mechanism

For each surface: render every unit to canonical bytes, with the doc-bearing keywords `description`, `summary`, and `example` removed only where the OpenAPI Schema, Operation, Parameter, or Response Object defines them as annotations, including on the schema of each entry under `properties`, and never when the keyword is itself the name of an entry under `properties`, a named map, or a payload (a real property named `description`, such as `QueryCatalogEntry.description`, stays in the hash while its own `description` annotation is stripped); hash the bytes with SHA-256; compare the map of unit names to hashes, the recomputed root, and the version, with the hash file. On mismatch the test fails and its message lists the added, removed, and changed unit names and the regeneration command. With `OMNIGRAPH_UPDATE_COMPAT` set, the test writes both files, the hash file including the current version constant, and returns; the file and the constant therefore cannot disagree after a regeneration. The check runs in the CI `test` job, with no new workflow. A green check means exactly this: the checked-in hash file equals the hashes, the root, and the version the code at this commit produces, and nothing more.

| Surface | Constant (crate) | Renderer, file, and test (crate) | Unit | Rendered from |
|---|---|---|---|---|
| HTTP wire | `HTTP_API_VERSION` (`omnigraph-api-types`) | `omnigraph-server` | each `components.schemas.<name>`; each `<METHOD> <path>` operation; each `components.securitySchemes.<name>`; one `document` unit holding every top-level field except `paths`, `components`, and `info.version`, plus every `components` entry that is not a schema or a security scheme | slices of `served_openapi()`; an operation unit includes the path-level fields it inherits; `info.version` becomes `<major>.<minor>` and stays out of every unit, so a version bump alone moves no hash |
| CLI JSON | `CLI_JSON_VERSION` (`omnigraph-cli`) | `omnigraph-cli` | each `--json` output: one per command path, and one per flag-selected shape where a command prints different roots by flag (`read --format jsonl` included); the change-feed documents the stitched writers produce are units of their own | `utoipa::ToSchema` derived on the CLI-private types and the cluster-plane outputs (utoipa added to `omnigraph-cli` and `omnigraph-cluster`); every `--json` root has a `ToSchema` schema, enforced by the bound `T: Serialize + ToSchema` on `print_json`; every `--json` root that is a `serde_json::Value` today (the four maintenance envelopes, the two inline `json!` sites, the managed control-plane results) becomes a named DTO, and a unit whose root schema is `AnyValue` is refused; the unit map is an explicit registry in one file, command path to schema, maintained by hand, and the hand-written writers (change feed, `jsonl`) are enrolled against a schema each with a test that their bytes validate; a unit's bytes are the root schema plus its reachable `$ref` closure, cycles ordered by name, so a nested field change (`QueriesListItem` under `QueriesListOutput`) moves the unit; a unit whose root is an api-types type that the HTTP surface enrolls (`schema:<Name>` present in the HTTP hash file) is a reference to that unit carrying the target's current hash (`{"ref": "http_api/schema:CommitListOutput", "hash": "<that unit's hash>"}`), so a shared root's change moves both surfaces' maps and both versions bump, since CLI consumers see the new shape too; the reference only spares a second rendering; an api-types type the HTTP surface does not enroll (`BlobStatOutput`, which the CLI builds from `HEAD` headers and `served_openapi()` never emits) is hashed under the CLI with its closure, since crate ownership does not decide surface ownership |
| GQ language | `GQ_LANGUAGE_VERSION` (`omnigraph-compiler`) | `omnigraph-compiler` | each rule of `query.pest`; and, in a second versionless file `gq_cases.hashes.json` listed under `surfaces` as `gq_cases` with a root only, each GQ logic case's query-step expectations (RFC 0045), the language's behaviour written down, read by the compiler's test from `crates/omnigraph-gqt/cases/` by path since the `test` job excludes `omnigraph-gqt` | the rule as `pest_meta` parses it: name, modifier (`@`, `$`, `!`, `_` or none), and expression, rendered with literal bytes, alternative order, and quantifiers kept, and only comments and formatting outside literals dropped; a case unit is the `expect unordered`, `ordered`, `error:`, and `shape` sections of the case's `--- query` steps as text, so a changed expectation moves a hash and names the case, while a new case adds a unit and a case with no `--- query` step has none; every section of a `--- mutate` step (`expect ok`, `expect affected:`, `expect error:`) and of a merge step (`expect outcome:`) is engine behaviour and stays out; the `gq_cases` file carries no version and is exempt from the floor's version and removal rules, since the case set moves with every bug fix and a language version that moved with it would say nothing to a client |
| PG language | `PG_LANGUAGE_VERSION` (`omnigraph-compiler`) | `omnigraph-compiler` | each rule of `schema.pest` | the same |
| `cluster.yaml` | `CLUSTER_CONFIG_VERSION` (`omnigraph-cluster`) | `omnigraph-cluster` | each configuration type, `QueriesDecl` included | `ToSchema` derived on `RawClusterConfig` and its nested types. The derived schema does not carry serde aliases or other deserialization attributes; accepted aliases are pinned by a separate list test (Evidence and tests) and their removal is a major bump with an unchanged unit map |
| Policy | `POLICY_VERSION` (`omnigraph-policy`) | `omnigraph-policy` | each Cedar entity type, action, and common type; each policy-file type (`PolicyConfig`, `PolicyAllowRule`, `PolicyTestConfig` and what they nest) | Cedar: `cedar_policy::SchemaFragment::from_cedarschema_str(policy_schema_source())` rendered with `to_json_value`, sliced per `entityTypes.<name>`, `actions.<name>`, and `commonTypes.<name>` under the `Omnigraph` namespace, so a `RequestContext` edit moves a unit; a second namespace in the schema is refused. Policy file: `ToSchema` derived on the policy crate's file DTOs; the file's `version: 1` is the surface's major, asserted equal to `POLICY_VERSION.0` by a test |
| Storage format | `INTERNAL_MANIFEST_SCHEMA_VERSION` (`omnigraph-engine`; u32, owned by RFC 0064 and the "One storage format version" draft) | none | listed, not hashed | unchanged |

Unit keys, the hash file's map keys: `schema:<Name>`, `op:<METHOD> <path>`, `security:<name>`, and `document` (HTTP wire), `cmd:<command path>` and `cmd:<command path> <flag>` (CLI), `rule:<name>` (GQ and PG), `case:<file stem>` (GQ), `type:<Name>` (`cluster.yaml`), `entity:<Name>`, `action:<name>`, `common:<Name>`, and `file:<Type>` (policy). A key is unique within its surface because it is the key of the map the unit is rendered from, and the renderer refuses a collision.

Ownership is split for the HTTP wire on purpose: `omnigraph-api-types` owns the constant and the DTOs and stays free of server internals; `omnigraph-server` owns `served_openapi()`, the hash file, and the check test, and exports the file for the listing.

Why `cluster.yaml`'s major is not new: the file's `version` field, refused unless 1 in `validate_cluster_header`, already is a major version. `CLUSTER_CONFIG_VERSION.0` is asserted equal to it by a test; the minor is the addition.

### The listing

`CompatOutput` in `omnigraph-api-types` (`ToSchema`, so it is itself an HTTP unit) is `{ "surfaces": { <name>: SurfaceCompat }, "storage_format": u32, "root": String }`, the last a SHA-256 over the canonical bytes of the record without its `root` field, the `surfaces` map and `storage_format` together, so one comparison answers whether two builds of the same kind (server against server, CLI against CLI) are structurally identical across every surface each reports, the storage stamp included; it is not comparable between a CLI and a server, whose enrolled sets differ by `cli_json`; with `SurfaceCompat` in two forms fixed in phase 1, `{ major: u16, minor: u16, root: String }` for a versioned surface and `{ root: String }` for a root-only one (`version` absent, never `0.0`), and surface names `http_api`, `cli_json`, `gq_language`, `gq_cases` (root only), `pg_language`, `cluster_config`, `policy`; `storage_format` is a bare integer beside the map, with no hash file and no unit map. A root-only hash file omits `version`, its check test compares units and root only, and its release line reads `<surface name> root changed: <keys>`; `storage_format` prints `storage_format <n>`. A surface appears under `surfaces` only once its hash file exists in the build that serves the record; an unenrolled surface is absent, never null and never given an invented root, so a phase 1 server reports `http_api` alone and the record grows with each phase. The server's record never carries `cli_json`; the CLI's own record, from `omnigraph version --json`, carries it and every surface the CLI's build embeds. `HealthOutput` gains a `compat: CompatOutput` field. `GET /compat` returns `CompatDetailOutput` (`omnigraph-api-types`): the same record plus `units: { <name>: { <unit key>: <hash> | {"ref": ...} } }` for the same enrolled surfaces. The CLI prints the same record for its own build, and the `omnigraph-http-api` header carries the HTTP wire's version and root in both directions. `/compat` promises this: the units it reports are the file the binary embedded, which the check test holds equal to the code at the commit the binary was built from.

`/compat` is a flat, unprefixed path like `/healthz`.

## Invariants

- **Integrity failures are loud (8).** A major mismatch between CLI and server is a typed outcome naming both versions, never a silently degraded call. The server's admission refusal precedes any effect; the CLI's response-side outcome says only that the response is incompatible and that the request's effect is not established, never that no write happened.
- **Query semantics are typed structures (9).** The `rule:` hashes record syntax; the `case:` hashes record expectations already written as text in `.gqt` files; neither introduces a side table the planner reads.
- **One source of truth, cheaply derived (12).** The code is the authority for every surface; a hash file is a derived witness the check test reconciles, the same status `openapi.json` and `detector_census.txt` hold today. The binary embeds the file only to report it; no decision inside the engine reads it.
- **Evidence matches the boundary (13).** Each check tests the layer whose contract changed, in the crate that owns it.

Deny-list: "maintained parallel truth or cold full-history reconstruction per request" is the nearest item. The hash files are not a second truth: they cannot be edited to any effect, since the test regenerates from code and fails on disagreement. No other deny-list item is touched; no support boundary changes.

## Compatibility and reversibility

Storage: unchanged. Wire: four additive changes, the `compat` field in `HealthOutput`, the `GET /compat` route, the `omnigraph-http-api` header in both directions, and the `api_version_mismatch` error code, all present from `HTTP_API_VERSION = (1, 0)`, so no consumer ever sees a 1.0 wire without them. `info.version` in `openapi.json` changes meaning from the crate version to the API version, a visible change to anyone generating a client from the document. Chosen over keeping the crate version there with an `x-api-version` extension beside it: one number with one meaning, the document stops changing on every release, and nothing in the repository generates a client from the field today.

Mixed-version fleet: an old server with a new CLI ignores the header on the request and sends none on the response; the CLI warns once and continues, and its writes reach the old server unchecked, the same as today. A new server with an old CLI receives no header, admits the call as it does today, and sends a header the CLI ignores. Refusal happens only when the request carries the header and its major differs or it does not parse, and then at admission. Behind a load balancer the admission check runs on the server that executes the request, so the refusal and the effect are decided by the same process.

Versions describe the states of `main`: two branches that bump to the same number conflict on the hash file's `root` line at rebase, so `main` holds one root per version, and a same-version-different-root warning names a build off `main`.

Reverting: delete the seven hash files and seven units files (six surfaces plus `gq_cases`), the check tests, the constants, the `compat` field, the `/compat` route, the header, the error code, the two CI steps, the two scripts, the `check-docs.py` rule, the deprecation lists, and `omnigraph version --json`. Nothing persisted refers to any of them.

## Alternatives

**Do nothing.** The HTTP golden keeps catching HTTP drift. The CLI-private types, the Cedar schema, and additive config fields keep changing silently, and no number ever says which release changed what. Rejected: the question the RFC exists for stays unanswerable for six surfaces.

**Simplest competitor: goldens without versions.** Extend the existing idiom to the six surfaces as whole-surface goldens and add no version constant. This catches every change and names it in a diff, at lower cost than this RFC, and it is where Polars' own comment points: the hashes, not the version, check compatibility. It fails on the one thing a diff cannot say: whether the change is breaking. A client or a release note needs a number that moved, and a whole-surface golden diff has no place to record the author's breaking-or-additive judgment. The version constant is that place, and it costs one line per surface. Kept.

**Hash files without the goldens, the pure Polars shape.** Replace `openapi.json` with the hash file. Rejected: the golden's diff shows the actual schema change where a hash diff shows only that a type moved, and the document is what a client generator consumes. Both artifacts stay; both derive from `served_openapi()`.

**Hash the query AST instead of the grammar.** Rejected: the query AST and IR carry no serde and are rebuilt at boot from the stored `.gq` text (`StoredQuery.source` in `crates/omnigraph-server/src/queries.rs`), so the grammar is what every persisted query is written against.

**Semantic OpenAPI diff in CI (oasdiff or similar) instead of a hand-set version.** Computes breaking-or-additive without an author's claim. Rejected as a replacement: HTTP-only, and its classification rules are the tool's. Adopted as a floor: phase 4 runs it over the base and head `openapi.json` and refuses a minor bump when the tool reports a breaking change, so the human classification is checked on the one surface a tool can read.

**Precedent audit.** Whole-artifact goldens regenerated under an environment variable: `openapi.json` (`OMNIGRAPH_UPDATE_OPENAPI`), `detector_census.txt` (`DST_REGEN_CENSUS`), `cost_table.txt` (`DST_REGEN_COSTS`); this RFC reuses the idiom and the placement of the test in the owning crate. Hand-set version constants with refusal: `INTERNAL_MANIFEST_SCHEMA_VERSION` (RFC 0064), `SCHEMA_IR_VERSION_FEATURES` with its feature-name set (RFC 0040), `RawClusterConfig.version`; this RFC adds the minor and the per-unit record. Divergence from the nearest precedent: `openapi.json` is one file for the whole surface, the hash file is per unit; the reason is that the reviewer's question is "which units moved", which a 178 KB document's diff answers slowly and a sorted map answers on sight.

## Evidence and tests

- One check test per surface, in the owning crate, beside the tests that own the surface today: `crates/omnigraph-server/tests/openapi.rs` (next to `openapi_spec_is_up_to_date`), the CLI's `tests/`, `crates/omnigraph-cluster/src/tests.rs`, the policy crate's unit tests, the compiler's parser test modules. These are Rust tests, not GQ logic cases, because they read and write files and an environment variable, which the `.gqt` format does not express.
- A test per surface that a regenerated file round-trips: regenerate into a temporary path, compare with the committed file, assert equal on a clean tree. A canonical-bytes vector test: one fixed input, its expected bytes, its expected hash.
- Renderer tests that a real change moves the unit and a doc edit does not: a property named `description` removed or retyped (HTTP), a nested field removed under a `$ref` (CLI), a rule's modifier removed and a quoted literal's spaces doubled (GQ), `bearer_token` changed to another scheme (HTTP `security:` unit), a `RequestContext` field retyped (policy `common:` unit).
- `cluster.yaml`: a test that `CLUSTER_CONFIG_VERSION.0` equals the file version `validate_cluster_header` accepts, and a pinned list of accepted serde aliases (`provider` on `EmbeddingProviderConfig.kind` today) that fails when one is removed. Policy: the same equality test between `POLICY_VERSION.0` and the policy file version.
- HTTP: the existing OpenAPI contract tests extend to `CompatOutput`, `/compat`, the header in both directions, and the error code; a test that the served root hash equals the one computed from the checked-in file; a server test that a mismatched request major is refused before any write (a `DELETE` on a branch leaves the branch); a CLI test against a spawned server covers the response cases (same major, different major as `api_version_incompatible_response` with the status kept, lower minor, absent, malformed) and the same-version-different-root warning, on a JSON path and on a streamed path, with stdout byte-clean under `--json`; a test that a successful mutation followed by an incompatible response header yields the response outcome, not the admission one; a listing and a release-block fixture that contain `gq_cases` and `storage_format`; a test that retires one CLI command through the CLI's deprecation list while its HTTP target stays.
- The phase 4 floor: a CI step in the `test` job that compares each hash file's unit map and version between a base and a head tree, and fails when the version decreases, when a unit key present on the base is absent on the head without a strictly larger major, or when a hash file present on the base is absent on the head. A hash file with no base counterpart is a first enrollment and passes. A moved unit map with an unchanged version fails; a changed version with an unchanged unit map passes (the reviewer demands the regression case). For the HTTP wire the step also runs a semantic OpenAPI diff (oasdiff, pinned) over the base and head `openapi.json` and fails a minor bump the tool classes as breaking. The step also reads the units files and each surface's deprecation list at the newest release tag that is an ancestor of the head: a removed unit key whose rendering there carries no deprecation marker and whose list did not name it fails; `gq_cases` is exempt from the version and removal rules. The refs per event: a pull request compares `github.event.pull_request.base.sha` with the head; a push to `main` compares `github.event.before` with the pushed commit; tags and manual dispatch name no baseline and the step is skipped and reported as skipped. The job fetches the base commit and the release tags explicitly, since its checkout has no history; a baseline the event names that cannot be fetched fails the step rather than passing it.
- The cross-version job: the previous release's CLI (installed with `scripts/install.sh` and a `VERSION` pin, as the upgrade suites install theirs) against a server built from the head, started with `--unauthenticated` and loaded from the checked-in fixture, through a checked-in command list, failing on any error except the admission refusal of a differing major, which it reports and passes; on pull requests and pushes to `main`.
- GQ case units: a test that editing a query-step `expect` section of one case moves exactly that case's unit, that editing a `--- mutate` outcome moves nothing, that adding a case adds one, and that the `gq_cases` file carries no version.
- Releases: `scripts/compat-release-block.py` with a test over two fixture tag trees (one surface bumped, one unit removed, one first enrollment) and the `check-docs.py` rule that a `docs/releases/v*.md` file carries the block the generator prints for its previous tag; the rule runs in the existing documentation check on every pull request.
- Surveyed: Polars `dsl-schema` (`crates/polars-plan/src/dsl/plan.rs`, `build.rs`, `src/bin/dsl-schema.rs`, `.github/workflows/test-rust.yml` job `check-dsl-schema`, at `e7868fec77`).

## Rollout

Each phase is one PR and ships on its own. Phases land only after acceptance: the CLI mismatch check is product behavior, and a draft claims no authority over it.

1. **Mechanism and the HTTP wire.** `HTTP_API_VERSION`, canonical bytes and its vector test, `crates/omnigraph-server/compat/http_api.hashes.json` with its root hash and `http_api.units.json` beside it, the check test, `CompatOutput` in `HealthOutput` with `http_api` as its only enrolled surface, `GET /compat`, the `omnigraph-http-api` header in both directions and its admission check with the `api_version_mismatch` error code, `omnigraph version --json`, the CLI's one response-check seam, the `AGENTS.md` route. `implementation` moves to `in-progress`.
2. **CLI JSON, `cluster.yaml`, policy.** Three constants, three hash files with their units files, three tests; `ToSchema` derived where a surface has no schema render, utoipa added to `omnigraph-cli`, `omnigraph-cluster`, and `omnigraph-policy`; the `print_json` bound; every `Value` root becomes a DTO; the policy-file DTOs join the policy surface. `implementation` moves to `partial`.
3. **GQ and PG grammars.** Two constants, two hash files with their units files, one test module over the `pest_meta` rendering (`pest_meta` added to `omnigraph-compiler` as a dev-dependency, at the version `pest_derive` already locks); the GQ case units in their versionless file; the two grammar surfaces' deprecation lists.
4. **CI floor, cross-version job, release block.** The base-versus-head step in the `test` job with the per-event refs above, the pinned semantic OpenAPI diff on the HTTP wire, the deprecation rule, the cross-version CLI job; `scripts/compat-release-block.py`, its `check-docs.py` rule, and the tag fetch in the documentation job, with the block required from the first release note cut after this phase. `implementation` moves to `complete`.

Until phase 4 the version rule is reviewer-enforced, as in Polars.

## Unresolved questions

Decided by the maintainers on this PR, before acceptance:

1. The policy surface ties `POLICY_VERSION.0` to the policy file's `version: 1`, so a Cedar-only major bump refuses every deployed policy file. Keep one version for the surface, or split the Cedar schema and the policy file into two versions under one surface.
2. The admission refusal has no bypass, where Polars' hash refusal has `POLARS_SKIP_DSL_HASH_VERIFICATION`. Keep lockstep as the contract (CLI and server majors always match in a supported deployment), or add an operator bypass for emergencies.
