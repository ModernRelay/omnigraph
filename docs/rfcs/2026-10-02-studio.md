## 1. Summary

Add `omnigraph studio`: a browser UI for inspecting and editing graph records, with views of types, schema, branches, and commits. It runs locally from the existing CLI and uses the existing HTTP API. The first public release includes cell edits, adding rows, and deleting rows through conditional mutations.

This RFC requests approval of three decisions:

| Decision | Recommendation | Reason |
|---|---|---|
| Product scope | Support inspection and editing on both local cluster folders and already-running servers. | Developers can browse and change graph data through one UI using existing server contracts. |
| Distribution | Keep UI source in this repository, build it before compiling the CLI, and embed the generated assets in the binary. | Users receive one executable, and UI/API changes ship together without committing generated files. |
| Server integration | Add a small public route-extension API to the server crate for local boot mode. | The CLI can serve the UI and graph API on one loopback listener using the existing server runtime. |

Acceptance establishes these boundaries. The linked implementation plans provide optional detail for review and may change within those boundaries.

---

## 2. Motivation

The CLI exposes graph data, but table output is cumbersome for exploring unfamiliar types, inspecting records, and understanding branches and history. Tower provides a hosted console; a developer inspecting a local cluster folder needs a UI that starts from the terminal and works without registering that cluster with a hosted service.

Studio makes graph inspection part of the local development workflow. An RFC is warranted because this adds a supported CLI command, a frontend build pipeline, and a public integration point in the server crate. Those choices create continuing maintenance obligations.

## 3. Usage

```bash
# Open a local cluster folder.
omnigraph studio --cluster ./company-brain

# Connect to an existing server.
omnigraph studio --server prod --graph knowledge
```

The command opens a local browser UI to browse types, records, schema, branches, and commits, and to edit cells, add rows, and delete rows.

- **Boot mode:** Serve an applied local cluster folder. Use attach mode if another server already serves it.
- **Attach mode:** Connect using the CLI's existing credentials and the server's permissions.
- **Edits:** Each action uses the commit returned with the original read as its write precondition. A `412` shows a conflict and reloads the view without retrying the edit. Keys remain immutable; edge edits follow the server's supported mutation rules.

Flags, lifecycle, and errors are detailed in [02 · CLI lifecycle and proxy](assets/2026-10-02-studio/plan/02-cli-subcommand.md); edit controls are detailed in [03 · UI and API usage](assets/2026-10-02-studio/plan/03-studio-crate-and-ui.md).

## 4. Design

- **Local serving:** Serve the UI on loopback. Boot mode uses the existing server runtime; attach mode proxies to the selected server and keeps credentials in the CLI.
- **Distribution:** Build the UI before compiling the CLI and embed its assets in the executable. Full CLI builds require a pinned JavaScript toolchain; generated assets are not committed.
- **API boundary:** Use existing HTTP routes for reads and conditional edits, with no new graph endpoints or direct storage access.

## 5. Invariants

- **Trust at the boundary (10).** Attach mode uses the existing server's credential and policy enforcement. Boot mode uses the server's explicit unauthenticated runtime on loopback. The browser supplies no trusted actor identity.
- **Bounded resource use (11).** Boot mode retains server limits. The attach proxy bounds request size and duration, streams bodies, and performs no silent retry.
- **One coherent view (3).** Each grid query reads one accepted snapshot and displays its returned commit. Separate requests may observe different commits; Studio must not imply that independently fetched counts and rows form one pinned snapshot.
- **A mutation publishes once (4).** Each submitted edit is one mutation request. Studio neither batches independent cell edits nor maintains a client-side write queue. The server validates and atomically publishes any effects.
- **One source of truth (12).** Studio uses the existing API and maintains no parallel graph state. It introduces no storage, publication, or recovery mechanism and requires no deny-list exception.

## 6. Compatibility and reversibility

The graph API, OpenAPI document, storage format, and standalone server binary remain unchanged. UI routes exist only in the process running Studio. The CLI gains a command and embedded assets; the server crate gains a public integration API.

Studio targets the server version shipped with it. Attach mode makes no blanket compatibility promise for older servers: unsupported routes or HTTP contract mismatches produce visible errors rather than an alternate execution path.

The feature can be removed without migrating graph data. Removing an advertised CLI command or public server API would still require a compatibility decision; absence of a storage migration does not make those contracts free to withdraw.

## 7. Alternatives

| Alternative | Why the proposed approach is preferable |
|---|---|
| Ship a separately installed or hosted UI. | Adds installation or hosting obligations and coordination between UI and server versions. Embedding keeps the shipped versions together. |
| Commit built UI assets. | Preserves a Cargo-only CLI build, at the cost of generated files in Git and CI drift checks. Building from source keeps generated output out of the repository. |
| Download UI assets during the Rust build. | Adds an external artifact dependency and coordination with a separate UI release. Building from the same checkout keeps UI and CLI versions together. |
| Always proxy, including boot mode. | Avoids the server API addition, but needs a second local listener and an extra request hop. This is the strongest alternative if maintainers reject route extension. |
